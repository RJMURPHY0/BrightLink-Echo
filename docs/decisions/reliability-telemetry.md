# Decisions: Reliability Telemetry

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-07-28` — Fleet reliability telemetry: new `error_events` Supabase table (run `supabase_error_events.sql` once; clients insert-own, super-admin select). The app logs `inject_failed` (structured `Injector.last_failure`: fg exe/class, method, partial WM_CHAR, elevated target, foreground-moved, exception — NOT merged for Live Typing failures, which never call `inject()` and would otherwise report a stale record from a previous dictation), `inject_false_success` (background WM_GETTEXT read-back, classic Edit controls only — telemetry ONLY, NEVER re-inject on a failed check: a false negative would duplicate the text; skipped under `auto_enter` and an empty control reads as unverifiable, both because submit-and-clear inputs would flood the log with phantoms), `mic_silent`/`transcribe_empty` (real audio, no words) and `mic_switched`. Events link to their transcription row via `transcription_created_at`. All writes fire-and-forget via `SupabaseLogger.log_error_event`.

- `2026-07-29` — Memory-pressure guard (v1.6.40). The "Tk_GetPixmap: Error from CreateDIBSection — Not enough memory resources" modal is Tk's one-shot warning when a widget repaint's CreateDIBSection fails; root cause on Ryan's machine was 18 idle `headroom.cli mcp serve` processes (one per Claude Code session, never exiting) holding ~12.6 GB commit on 16 GB RAM — the app was the messenger, not the leak (own GDI/caches audited clean: ui_render capped 512, fonts getattr-cached, icon extraction releases all handles). `memory_guard.py` samples GlobalMemoryStatusEx every 30s on a daemon thread; under pressure (load ≥90% / phys ≤400 MB / commit ≤1 GB) it logs a rate-limited `memory_pressure` error event (system stats + own private MB + own GDI count + busy flag, so a starved machine is distinguishable from an app leak) and, only when IDLE, clears regenerate-on-demand caches (`app_icons._raw_icon_cache`, `_hist_elide_cache`) + `gc.collect()`. Deliberate non-actions: never trims the working set (pages the ASR model out → next-dictation latency) and never clears PhotoImage caches (an image cleared while a canvas still displays it blanks that widget) — the latter is a source-level test invariant. Guarded by `tests/test_memory_guard.py`. Cooldown baselines use a None sentinel, not 0.0 — monotonic time counts from boot, so 0.0 suppressed the first report for an hour on a fresh boot.

- `2026-08-07` — Three hot-path costs removed (v1.6.51): the waveform re-sent the same `fill` to every bar 25×/sec while recording (~500 no-op Tcl calls a second) — the colour is applied once per run now (`_bars_active`); the live-caption tick re-applied a constant `width` to the Text widget, forcing a rewrap right before the `displaylines` measurement that had to wait for it; and `_exe_icon_cache_key` ran `os.stat` BEFORE the icon-cache lookup, so a history render did one stat per visible row on every search keystroke, resize and tab switch (now memoised for 10s per exe, so an in-place app update still refreshes its icon within seconds). Also: `ui_render`'s photo cache is keyed per Tcl interpreter, since a `PhotoImage` belongs to the root it was made in.

- `2026-08-07` — A dead audio stack no longer costs the whole session. Root cause of "Whisper just stopped working": the Windows Audio service (`Audiosrv`) hung under a live warm stream and was killed by Windows (System 7031 + AppHangB1 at 20:05:33; it had also died at 14:21:55 in the previous boot, with the app not running, so this is a machine fault, not one the app causes). PortAudio kept calling back throughout, just with **zero-filled buffers** — so `stream.active` stayed True, the heartbeat stayed fresh, and `_stream_looks_alive()`, which knows only those two things, judged the corpse healthy indefinitely. The watchdog could therefore never fire, and every press for the next three minutes captured nothing and buzzed. Two fixes: (1) `_audio_callback` now tracks a run of **bit-exact-zero** buffers (a live mic always carries a noise floor, so exact zeros mean the stream has lost its device), and the idle watchdog reopens after `_SILENT_STREAM_SECONDS` (25s) via `_stream_is_silently_dead()`/`_recover_silent_stream()`, with `_SILENCE_RETRY_BACKOFF` so a hardware-muted mic settles into an occasional retry instead of a reopen every 25s. (2) The `Recording too short` branch, which previously buzzed and returned with **no recovery at all**, now calls `_handle_dead_capture()`: if the hotkey was held ≥1.0s but under 0.3s of audio arrived, the stream is lying, so it fires `restart_warm` on a background thread and tells the user the mic reconnected. A genuine quick tap (held ≈ as briefly as the audio it produced) is unchanged. **The silence check is deliberately NOT folded into `_stream_looks_alive()`** — that runs on the press path via `start()` → `_ensure_warm_stream()`, and a muted mic reads as exact zeros too, so failing liveness there would cold-open the stream under a user who is already speaking and eat their first words. New events `capture_dead` and `mic_stream_silent` (`event_type` has no CHECK constraint, so no migration). Guarded by `tests/test_stream_liveness.py`, which pins the press-path invariant explicitly. NB: `_PREROLL_SEED_SECONDS` is **0.8**, not the 0.6 recorded in the 2026-07-23 entry above — 0.6 still clipped first words under load. The same test file now pins both it and the 1.5s ring, because they are the only two things governing how much pre-hotkey audio can ever reach a transcript.

- `2026-10-12`: **Slow presses and empty dictations reach the fleet log (v1.8.10).** "No speech detected" and "Recording too short" were only written to the local startup log, so "it didn't pick me up" could not be counted. They now also log `dictation_empty` (error, recording seconds, pre-roll seed, press timing). A press whose cue took over 150 ms, pill over 250 ms or capture over 500 ms logs `press_slow` with every mark (a cue after capture is the cold-mic path by design and is not counted; it is already `mic_press_recovered`). Each type is capped at 20 events per run. Checked live: an authenticated insert passes RLS for Ryan; for non-admin users the client's default read-back of the inserted row is refused by the super-admin-only SELECT policy, which the `returning=minimal` change in `supabase_client.py` (separate work) fixes.

- `2026-11-05`: **The speech model is kept in memory, and a slow stop now says why (v1.8.33).** Ryan: transcriptions stopped being instant and a restart fixed it. Logs for 367 dictations (28 Oct to 5 Nov): median stop-to-text 1 s, 19 at 4 s or more, the worst a 3 s clip taking 51 s, a 13.6 s clip 20 s, decode running at 0.1x to 2.6x realtime against about 9x normally. Slow was about four times as likely after 30+ minutes idle (6 of 40) as otherwise (13 of 327). The laptop reported memory_pressure hourly at 90-96% of 32 GB. Measured with a real Parakeet decode of a 13.6 s clip, `Code/echo-scratch/latency_bench/bench.py`: normal 1.5 s; every core busy 1.4 s (above-normal class wins); P-cores only, E-cores only, opting out of power throttling: no consistent gain; 40 s at 96-98% RAM: no trim, 1.5 s; **model really paged out: 4.7-5.9 s on the first decode**. One keep-warm pass after a page-out took 0.76 s and the next real decode 1.6 s; a pass over a resident model costs about 0.2 s (0.8 s CPU). PortAudio re-init every 2 minutes was tested for a leak (60 cycles, private bytes and handles flat): not the cause, left alone. A hard working-set floor is not shipped: EmptyWorkingSet ignored it in the bench, no test showed it helping, and it takes RAM from everything else. The old "never trim" stays. The bench also found that tests/test_supabase_history.py was deleting the real recordings folder on every full test run (clear_history's orphan sweep, since 12 Oct): fixed there, and that is why stored audio kept looking pruned. `model_warmth.ModelKeepWarm` runs a throwaway decode every 3 minutes on mains while the person is around (never during a dictation, stops after 30 minutes away) and straight away at a press after a minute's quiet, on any power. **Caught live on 5 Nov at 21:29:** the installed app had fallen from 848 MB resident to 148 MB (private still 1,911 MB) with 7.6 GB of RAM free; a press after that climbed back to 982 MB over 50 s, about 17 MB/s, and a 21 s clip took 57 s to appear with no commit on the way. So the page-in is the slowdown, and a real page-in is far slower than the bench's 700 MB in 3.5 s, which came back from the standby list. **What pushes it out is not established.** Minimising or hiding a Tk window does not (tested: 539 MB before and after, with and without a hard minimum). Two idle copies of the engine, one with keep-warm, one without, stayed resident for 23 minutes at up to 99% load until the run stopped itself, so that run does not show keep-warm beating nothing in the field. So new evidence ships with the fix: every stop logs `[Stop]` with wall, CPU and fault counts, a stop over 3 s logs `stop_slow`, a keep-warm pass over 600 ms logs `model_paged_in`. Wall far above CPU means waiting on memory or disk; if `stop_slow` keeps coming with `model_paged_in` silent, this theory is wrong and the search restarts from those numbers. Also fixed: `own_private_mb` and `own_gdi` read 0 in every memory_pressure report ever sent, through a handle call on the shared `ctypes.windll`.

- `2026-11-07`: **Echo closing by itself was the auto-update, and crashes can no longer go unseen (v1.8.35).** Ryan: Echo closed on its own and stopped working. Windows has no crash, hang or error report for Echo in the last 14 days and every restart in the logs for the last 7 lines up with a Windows restart or an update. On 6 Nov the 1.8.34 update closed Echo at 23:35:23, about 3 minutes after his last dictation while he was still at the laptop, and hotkeys only came back at 23:38:22 with RAM at 92 to 99 percent. The "Updated" pop-up that would have explained it failed on every update (`tk.Canvas(bg="")` raises TclError) and left an invisible topmost window behind. Now: `update_gate.safe_to_restart` waits for 10 minutes with no keyboard or mouse input anywhere in Windows (or 24 hours waiting, so an update still lands), a toast says it is updating, and the pop-up works. `crash_watch.py` keeps a run-state file, so the next run reports `app_crashed` (cause `native_crash` with faulthandler's trace, `vanished`, `main_thread_exception`, `hang_restart`, `restart_limit_reached`), plus `ui_hang` at 60 s with every thread's stack, a relaunch at 10 minutes hung when not dictating, and `ui_error` / `thread_error` once per distinct error. Reports wait in `crash-pending.json` until a signed-in insert succeeds. `RegisterApplicationRestart` has Windows relaunch after a crash; our own relaunches stop at 3 an hour. Reports hold event names, numbers, code locations and the scrubbed log tail, never an exception message or dictated text. They reach `error_events`, the BrightLink error log (`error_logs`, source whisper) and Telegram (cloud Hermes job `Echo crash watch` polling the RPC `echo_crash_feed`, which returns no person and no free text). Read them with: `select created_at, event_type, app_version, detail from error_events where event_type in ('app_crashed','ui_hang','ui_error','thread_error') order by id desc limit 20`.
