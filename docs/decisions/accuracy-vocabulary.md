# Decisions: Accuracy Vocabulary

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-07-04` — Parakeet made the primary engine for English because it beats whisper-large-v3 on accuracy at a fraction of the cost, so the upgrade pass became LLM `context_fix` only (a whisper re-pass would usually be a downgrade).

- `2026-08-14` — Custom Vocabulary and Snippets, both per account (v1.6.67). Two user-owned libraries, each a FULL PAGE reached from a Settings row (`_link_card` → `_switch_dash_tab("vocabulary"/"snippets")`, `‹ Back` returns to Settings). They join `_dash_content`'s grid like the other pages, so the atomic swap, wheel routing and repaint healing apply unchanged — rejected an inline card in Settings (a forty-row list buries every setting below it on an already-long scrolling page) and a Toplevel (every Toplevel here has cost a Z-order or DPI bug). A vocabulary entry is a TERM plus optional `sounds_like` mishearings: the term is fed to both engines via `_get_hotwords()`, the mishearings are corrected after transcription — **never the reverse**, since feeding "pipe drive" to the engine as a hotword biases it towards producing exactly the output the entry exists to correct. Both apply in `text_expansion.py` at the single post-processing point in `app.py` (right after `apply_spoken_commands`), vocabulary FIRST so a corrected term can complete a snippet trigger but never the reverse. Matching is deliberately conservative because this rewrites what the user actually said: whole word/phrase only via lookarounds (`\b` is wrong at both ends — a pattern may legitimately start or end with punctuation), ONE single-pass alternation so a replacement can never be re-matched (a loop cascades), longest pattern first, and a 3-character floor refused at entry time with the reason SHOWN. Sentence-start capitalisation applies to a vocabulary term only when it is entirely lower case, and **never to a snippet body** — a body is verbatim, and recasing one holding an email address gives "Ryan@ftc.co.uk". Storage is `config.vocabulary` / `config.snippets`, dicts keyed by account email exactly like `window_sizes` (`"_local"` while signed out, adopted by the first account that signs in); Supabase `user_vocabulary`/`user_snippets` (run `supabase/user_libraries.sql` once) sync between a user's machines, merged last-write-wins on `updated_at` with soft-delete tombstones — a hard delete loses to any machine still holding the row. The local copy is the source of truth at dictation time: the hot path only ever reads the in-memory list, so a missing table costs nothing. The old comma-separated `custom_vocabulary` Entry is replaced by the link row and migrated once into boost-only entries, with the legacy key LEFT IN PLACE so a downgrade still finds it. History's search bar was extracted to a shared `_search_bar()` used by all three pages. Guarded by `tests/test_text_expansion.py`, `tests/test_vocab_store.py`, `tests/test_library_pages.py`.

- `2026-08-17` — **Degenerate-repetition guard (v1.6.68), the missing hallucination layer.** Reported live: a user's dictation came back as "no, no, no, no, …" repeated dozens of times. Parakeet is an RNN-T *transducer* — at each step it may emit a token and stay on the same audio frame, so on degenerate input (dead/muted mic, heavy steady noise, a clipped fragment, an accent hitting a low-confidence region) the decoder can lock into a cycle and emit one token until its frame budget runs out. Whisper does the same through autoregressive looping, which is why it ships `repetition_penalty` — a penalty lowers the odds, it does not remove them. **Nothing caught it:** the silence floor and the Silero VAD gate in `asr_engine` only decide whether the model RUNS, never whether its output is sane, and `_FILLER_ONLY` matches only hesitation noises. The loop was injected into the user's document verbatim. New `hallucination.py`, applied inside BOTH engines' `_post_process` (so it covers batch, streaming chunks and live captions at one point per engine, and no future call path can bypass it): a unit of 1-4 words repeated 4+ times is COLLAPSED to 3, and an utterance that is *nothing but* one unit repeated 6+ times is SUPPRESSED to "" (the app already has a no-speech path; reporting nothing is honest where injecting "No, no, no." is not). Deliberately text-level, NOT a decoder parameter: `no_repeat_ngram_size` / a harder `repetition_penalty` suppress legitimately repeated words too and cannot be validated without a GPU-hours sweep, whereas a text rule is exact, cheap and unit-testable. Thresholds are set so real emphatic speech survives — three is reachable ("no, no, no, that is not what I meant"), four is not. The run's LAST occurrence is kept alongside the first ones so its terminal punctuation survives. Periodicity is found by extending token-by-token (`t[k] == t[k+n]`), NEVER unit-by-unit: a unit-aligned scan locks onto a shifted phase and strands a dangling fragment ("Honestly I don't know. … I don't" before the next sentence) — caught in test. Detections report `transcribe_repetition` to `error_events` via a module-level reporter app.py wires up (no CHECK constraint on `event_type`, so no migration). Guarded by `tests/test_hallucination.py`, which pins both directions — the loop cases AND the real-speech cases, since silently rewriting what the user said is the worse regression.

- `2026-08-17` — **Voice isolation was measured and deliberately NOT built (v1.6.69).** Ryan asked for it so music and background noise stop affecting accuracy. Measured on 20 of his own stored dictations (`%APPDATA%\FTC Whisper\audio` paired with `history.json`), mixed with interference at controlled SNR, scored as WER against Parakeet's own clean-audio output (which measures DEGRADATION FROM NOISE, the actual question, not absolute WER). Result: **music is a non-problem** — 5.0/6.1/5.9% at 10/5/0 dB, flat, i.e. the noise floor; and **zero** phantom words on noise-only clips at every level tested, including vocal-forward music, because the instrumental backing masks the vocal enough that neither the VAD nor the transducer latches onto it. Steady noise (fan/road) is moderate: 8.8/12.7/25.8%. **Other people's speech is the entire problem**: 20.0/47.2/83.2%, and it produced every phantom word measured. A Silero threshold sweep is useless against it — 0.40 → 31 phantom words, 0.70 → 31 — because the interference genuinely IS speech and Silero is right to call it so. Combined with the published finding that enhancement front-ends RAISE ASR WER on models trained on noisy data (artefact/distribution mismatch), a denoiser would have targeted the cases that are already fine and made them slightly worse. The real fix for the real problem is target-speaker extraction (enrol the user's voice, drop everyone else's); it is a much larger build and did not meet the "very low risk, must only improve" bar for this release. Harness kept in the session scratchpad (`noise_eval.py`, `phantom_eval.py`, `vocal_music.py`) — **re-run it before entertaining any future noise-suppression proposal** rather than re-deriving the numbers.

- `2026-08-19` — **"It's not getting the first word I say" was the VAD gate, not the capture (v1.6.71).** Four earlier releases chased this as a press-latency / pre-roll problem; this time it was measured. The stored WAVs in `%APPDATA%\FTC Whisper\audio` were paired with their `history.json` rows and re-transcribed with the Silero gate ON and OFF: with it OFF the leading words were all present, with it ON they were gone. Measured losses, all Ryan's own dictations: `"Can you give me a prompt…"` → `"Give me a prompt…"`, `"It's very very important…"` → `"Very very important…"`, `"I found another issue…"` → `"Found another issue…"`, `"I haven't had…"` → `"Haven't had…"`. Root cause: Silero decides where speech BEGINS from its own confidence curve, and a quiet first word sits under `threshold=0.40`, so `_vad_clip` cut it out and the model never saw it. `speech_pad_ms=200` cannot help — it pads a region Silero has already placed AFTER the missed word. Fix: `_VAD_EDGE_KEEP` (3.0s) extends the FIRST region back and the LAST region forward before splicing, then merges anything that now overlaps. The gate's real jobs are untouched: a clip with no speech at all still returns None (re-verified against digital silence, hiss at two levels, 50 Hz hum and real room tone — all still transcribe to nothing), and long noise-only stretches in the MIDDLE are still spliced out. **3.0s, not 1.0s:** 1.0s was tried first and still failed on a real far-field clip peaking at 0.030 where Silero placed its first region 1.9s late, which came back as "Contacts that scraped this week" instead of "I haven't had some scrapes this week" — the bound has to clear the worst measured onset error, not the average. Guarded by `tests/test_vad_edge_keep.py`.

- `2026-08-19` — **Investigated and NOT a bug: "it randomly inserted text I never said" (v1.6.71).** Reported with a screenshot showing `"my downloaded claude seems to be brocken Okay, my software."` in the Claude desktop app, where only "Okay, my software" had been dictated. The local history was searched: the app has never transcribed that phrase, in any form, in the 200 rows held locally — and `live_inject` is off in that config, so nothing else in the app could have typed it. The text was already in the box (the "brocken" spelling is a keyboard transposition, not something the ASR vocabulary produces). No code change; recorded here so the next report of phantom text starts from the history check rather than from a rewrite of the injection path.

- `2026-08-27` — **"It transcribed a fish and chip shop I never mentioned" root-caused: CRM names were in whisper's decoder prompt (v1.6.72).** A different failure from the v1.6.68 repetition loop, and nothing in the app could catch it. `fetch_contact_vocab` pulls 150 contact/company names from the estate CRM into `_get_hotwords()`, which went to BOTH engines. faster-whisper does not keep `hotwords` in a separate hint channel: `get_prompt` encodes them under `sot_prev`, **the same token slot as previous-transcript context** (verified in the installed package). Whisper therefore cannot distinguish "term to watch for" from "text that was just spoken", and on unclear audio it emits prompt content as dictation. Ryan's real cache holds `Prashad Indian Vegetarian Restaurant`, `andSons Chocolatiers`, `Shirt In A Box` — so the fabricated output was a fluent sentence about a business in his own CRM. Two things hid it: the prompt-echo guard in `transcriber._run` only tested `context_words` and **never `hotwords_str`**, and `_PHRASE_ARTIFACTS` only knows YouTube-isms. Compounding it, the query has **no ORDER BY**, so the 150 rows are an arbitrary, unstable subset that changes between syncs — which is why it looked random. Fix: managed/CRM terms are removed from the whisper path entirely (`_get_prompt_hotwords`, user's own reviewed vocabulary only) and kept on Parakeet's (`_get_hotwords`), where `hotwords_str` drives nothing but a whole-word casing fix on text the model already produced and therefore **cannot invent a word**. The echo guard now checks both prompt sources, and a suppressed echo reports `transcribe_prompt_echo` through `hallucination.report()` (the sink app.py already wires; no migration, no CHECK constraint). **The rule this establishes: a term list may only ever reach a decoder prompt if a human reviewed it. Correction can mis-fix a word that was said; a prompt can invent a sentence that was not.**

- `2026-08-27` — Managed vocabulary: CRM names finally do something (v1.6.72). They previously reached only Parakeet's casing pass, so a CRM name helped **only if the engine already spelt it correctly** — "Brightlink" heard as "bright link" was never fixed, because the phonetic net (`apply_vocabulary_fuzzy`) only ever saw hand-typed entries. Managed terms now go through that net too, tagged `managed`, which is also why the CRM side never needs to supply mishearing pairs: the net derives them. They are stored as a LIST (`_estate_terms`), never re-split from the comma-joined string, because real rows contain commas (`Forklifts Group West, Manteca`) and splitting invents terms. **Single-word managed terms take a strict tier** (`MANAGED_JW` 0.86 vs 0.70, min length 5, tighter length ratio, and refused outright if the word is ordinary English) because that is where the entire risk lives: a real CRM holds "Shell" and "Next", and `jw("shall","shell")≈0.88` clears even the strict floor while "shall" is not itself common-listed, so the span check cannot save it. Multi-word terms keep the normal gate: matching across consecutive words is constraint enough, and tightening them would only break the names safest to correct. `managed_variants()` adds the trading name ("Fosseway Freight Ltd" → "Fosseway Freight") and drops taglines after a colon; correcting to the registered name would be worse, since it appends "Ltd" to words nobody said. User entries are passed FIRST so a hand-typed term always beats a colliding managed one. `config.managed_vocab` is a separate kill switch from `vocab_fuzzy` — a bad CRM sync must not cost the user the net on their own words. Validated against the real corpus: 150 real CRM terms over the 200 real transcripts in `history.json` rewrite **exactly zero**. Guarded by `tests/test_managed_vocab.py`, which pins both directions plus that corpus run. **The metaphone gate stays the primary firewall and is pinned by test** ("lightning" vs "lighting" is not a near-miss to chase; loosening it is what would make the whole pass unsafe).

- `2026-08-29` — **The warm mic stopped typing the room (v1.6.73).** Reported with a screenshot: "Hello, my name is Ryan" spoken aloud, THEN ALT+V, THEN "Whisperflow" — and the whole lot was injected. Root cause is the pre-roll seed itself: `start()` unconditionally prepends `_PREROLL_SEED_SECONDS` (0.8s) of pre-hotkey audio, and 0.8s of Ryan's speech is five words. Proven by slicing his own stored WAV: the first 0.8s of `20260829172915541914.wav` transcribes to "Hello, my name is Ryan.", the remainder to "Whisper flow." Nothing downstream could have caught it — the audio is real speech, so the VAD gate, the silence floor and the repetition guard all correctly pass it through. New `_seed_cut_index()` decides where the dictation actually starts: only ONE thing in the seed can belong to it, the run of speech still going when the key landed, so that run is measured and kept **whole** if it is under `_SEED_RUN_MAX` (0.45s — a word begun a beat early) or dropped **whole** if it is longer (the user was already talking). Everything older goes either way. Four things are load-bearing and each was measured, not reasoned:
  1. **Never cut part-way through a run.** Trimming inside one turned "Host all recent changes" into "Post all recent changes" — half a word is worse than none. `_SEED_ONSET_PAD` (0.10s) additionally reaches back over the pause in front, because an unvoiced onset (/h/, /t/, /s/) carries almost no energy and the level test puts the run's start just after it.
  2. **Replace, never delete.** Shortening the clip moves the first real word closer to the start of the audio and the transducer decodes its opening phoneme differently. Overwriting in place leaves every sample where it was.
  3. **Room tone at a quarter of the floor** (`_SEED_FILL_GAIN`), A/B'd over 60 real dictations. At the full floor the fill is decoded itself ("I in Whisper Flow"); at 34 dB down the *attenuated speech* is still decoded verbatim ("Hello, my name is Ryan") because the envelope and formants survive a gain change; exact digital zeros shift neighbouring words ("testing" → "test him"). Only floor×0.25 left every untouched dictation untouched.
  4. **The threshold comes from `_noise_floor`, which is now tracked while IDLE as well as while recording.** A window that is wall-to-wall speech contains no floor of its own, and a percentile taken over speech reads ~10 dB under the peak and calls the whole utterance a pause.
  Validated against the real corpus: of the last 60 stored dictations, 11 change, and every one is either the leak being removed ("Yes sir. Architecture." → "Architecture.", "Paradigm shit. Whisper flow." → "Whisper flow.", "Where is it straight off the diarization?" → "Diarization.") or unchanged first words. `_PREROLL_SEED_SECONDS` stays 0.8 — it is now a ceiling, not the amount used — and `recorder.last_seed_ms` reports what actually survived (also printed on the start line). Guarded by `tests/test_seed_trim.py`, which pins both directions: the leak cases AND the onset cases, because silently dropping a word the user did say is the worse regression and is exactly what v1.6.71 spent a release chasing.

- `2026-08-31` — **Stutter / false-start collapse (v1.6.74).** Reported with a real example: "push all most **rec** recent changes" should inject "push all most recent changes" — the aborted fragment dropped, the completed word kept. This is a disfluency the engine transcribes *correctly* (it was said), distinct from the `hallucination.py` decoder loop (text nobody said), so it lives in a new `disfluency.py` with `destutter()` called inside BOTH engines' `_post_process` right after `hallucination.clean` — the one point every path (batch, committed chunk, live caption, upgrade) flows through, same rule as the loop guard. Because it deletes words the user genuinely said, it collapses only two narrow shapes: (1) a **false start** — a short fragment that is a strict, *non-inflectional* prefix of the next word and is not itself an ordinary word ("rec"→"recent", "prob"→"probably", "config"→"configuration", "re resize"→"resize"); (2) a **function-word double** — an exact repeat of a never-validly-doubled function word ("the the", "I I", "for for", "do do"). Two guards make it safe and each was necessary: a **common-word list** (so "the theory", "he helps", "in industry" are untouched — without it "the theory" collapses to "theory") and an **inflection guard** (so "car cars", "read reading", "help helped" are two real words, not a stutter). Emphatic/grammatical doubles are never collapsed ("very very", "no no", "had had", "that that" — none is in the collapse set), and a sentence boundary is never crossed. Whitespace is span-preserving: only the fragment and the single space beside it go, so paragraph breaks survive. **The safe direction is to UNDER-correct** — a missed stutter is one word too long, a wrong deletion changes what was said. Validated against the 200 real transcripts in `history.json`: **24 change, every one a genuine stutter, zero false positives, zero newlines lost.** Detections report `transcribe_stutter` via the sink app.py already wires (no CHECK constraint, no migration). Always-on with no config toggle, matching `hallucination.clean`'s treatment in the same location — the guards, not a switch, are what keep it safe. Guarded by `tests/test_destutter.py`, which pins both directions plus a corpus regression test that fails if any real transcript is ever rewritten into a shape neither rule explains. **Do NOT add abbreviation-like fragments (`rec`, `prob`, `def`, `config`, `impl`) to `_COMMON_WORDS`** — those are exactly what the feature exists to collapse; `rec` was mistakenly listed at first and silently blocked the reported case.

- `2026-09-09` — **The app learns the phrases you actually say, and uses them to fix the ones it mishears (v1.6.77).** Asked for directly: score how sure the recogniser was, keep the phrases that come up again and again, and boost them so a near-miss resolves to what the user really says. The confidence is **real, not a proxy** — Parakeet's decoder already computes per-token log-probabilities and onnx-asr will hand them over through `with_timestamps()`, which is the same decode plus one `log_softmax` per EMITTED token (microseconds on a whole dictation, measured), so asking for it costs no stop latency; the whisper fallback supplies its segment `avg_logprob`. `asr_engine.transcribe(conf_out=[...])` fills a caller-supplied list with `(word, confidence)`, and **only passes whose text is KEPT get one** — the caption preview throws its hypotheses away, and folding those in would repeat words and destroy the alignment. **The two gates are deliberately opposite**: a phrase is only LEARNED from words the engine was SURE about (≥0.75 — counting a shaky span is learning the mistake and then enforcing it), and only ever REWRITES a span the engine was UNSURE about (<0.55 — where it was confident it heard "the sell", it heard "the sell"). Unknown confidence fails BOTH closed. Everything runs on the finished transcript at app.py's one post-processing point, after injection is already decided: measured 1.2ms on a median dictation and 16ms on a 672-word one against a full 200-phrase store. **The corpus run is what shaped the thresholds, and it caught three real corruptions the first draft shipped**: `"to main" → "domain"` (identical metaphone, jw 0.889 — and Ryan says "push it to main" in almost every dictation), `"really a" → "really"` (jw 0.97 on the collapsed letters, **deleting a word he said**) and `"actual" → "actually"` (jw 0.95, a different word). Three rules killed all of them: a candidate span must itself pass the learning filter (so no match reaches over a function word at either edge), a cross-word-count match must be near-identical (jw ≥0.95) and may never be SHORTER in letters than the span it replaces, and the length window is the re-spelling one (0.82-1.22, not the managed tier's 0.7-1.4). Result: the adversarial run — every word of all 200 real transcripts marked low-confidence, store learned from those same transcripts — rewrites **exactly zero**, at three different hedging levels, while `"bright link" → "Brightlink"`, `"prospect until" → "prospect intel"` and `"leed finder" → "lead finder"` all still fire. A **single** learned word additionally requires the engine to have fumbled something that SOUNDS like it (keyed by metaphone, because when it mangles "Brightlink" what it writes is "brightling" — the code is the only thing the mistake and the target share): without that the store fills with "actually" and "really", which the recogniser never gets wrong and boosting cannot improve. Learned phrases reach **whisper's** `hotwords=` (a real decoder boost, capped at 40, most-said first) but deliberately **NOT** Parakeet's, whose `hotwords_str` only drives a per-term casing regex — 200 phrases there would buy nothing and cost 200 regex passes per dictation. Storage is local and per-account (`%LOCALAPPDATA%\FTC Whisper\phrases\<account>.json`, debounced onto a daemon thread), not a sync table: these are statistics about one person at one keyboard. Visible and editable at Settings → Phrases You Say Often (read-only rows with a Forget action — nothing was typed, so there is nothing to edit; Forget drops the COUNTER too, or a rejected phrase climbs back over the threshold next week), kill switch `config.learned_phrases`. Guarded by `tests/test_phrase_learning.py` (32, including the corpus regression and a named test for each of the three measured corruptions) and `tests/test_phrases_page.py` (16).

- `2026-09-09` — **A CRM name may not change a number the user said (v1.6.78).** Two red tests were sitting in the suite; one was a genuine bug the other had been masking. **Double Metaphone cannot see digits at all** — `"company23"` and `"company342"` both encode to `KMPN` — so the phonetic firewall, which is the PRIMARY gate in `apply_vocabulary_fuzzy`, waved them straight through, and the long shared prefix then scored jw 0.958, over even the strict managed floor of 0.86. Real dictation was being rewritten: `"Company 23"` → `"Company 342"`, and a bare `"company"` → `"Company 28"`. Not an edge case — **65 of the 150 terms in the live CRM cache carry digits**, so it covered most of the managed vocabulary. The gate now requires the digit runs of the span and the term to be IDENTICAL (`_digits()`), which is equality rather than a ban: `"Companie 342"` → `"Company 342"` still corrects, while a span with no digits can never gain one and a span with digits can never lose them. Inventing a number nobody said is the worst thing this pass can do. Applies to hand-typed terms too, because the hole is in the encoder, not in the tier. Pinned by `tests/test_managed_vocab.py::DigitTests` (5).

- `2026-09-09` — A regression fixture may not be able to expire (v1.6.78). `test_destutter`'s "the two known stutters are actually fixed" read its examples out of `history.json` — a **rolling 200-row cache of whatever Ryan said most recently**. It passed for weeks, then went red the day the reported "rec recent" dictation scrolled out of the window, for a reason that had nothing to do with the collapser (whose sibling corpus test was green throughout). The two examples — one per rule, a false start and a doubled function word, both real dictations — are now literals in the test file, with an assertion that each fixture actually pins a COLLAPSE (a fixture asserting "unchanged" pins nothing). The live-corpus check survives as a belt-to-the-braces that SKIPS when the cache no longer holds the example instead of failing. **Rule for this repo: a corpus test may assert an invariant over whatever the corpus happens to hold, but a named example belongs in the test.**

- `2026-09-21`: **One spoken word may not become a multi-word CRM name on the loose floor (v1.6.81).** The managed-vocab corpus test had been red since 2026-09-17, and by now it was a live bug: a CRM name "The Ark" turned Ryan's "going dark" into "going The Ark" and "dark mode" into "The Ark mode" (TRK both ways via the secondary code, collapsed letters jw 0.75 against the 0.70 multi-word floor). Two parts. (1) The 2026-09-17 function-word rule (patch from worktree adoring-solomon-fd34cd) is now in: a managed name may not absorb function words it does not carry, which fixed "they work" -> "The Ark" and "room and it" -> "Raymond Wood". (2) New: a ONE-word span takes the strict single-word tier (`MANAGED_JW` 0.86 and the tighter length window) whatever the name's length, because the multi-word floor is only safe when the match has to hold across consecutive spoken words, and here there is one. Near-identical merges still correct ("fosseway" -> "Fosse Way", jw 1.0). Suite fully green for the first time since 2026-09-17. Pinned by `tests/test_managed_vocab.py::FunctionWordTests` (mutation-checked: dropping the one-word rule fails both "dark" cases).

- `2026-09-21`: **"like" is a function word to the managed tier (v1.6.82).** Found by the corpus test the same evening, live in v1.6.81: a CRM name "Proseal UK" arrived in `estate-vocab.json` and turned a real 2026-09-09 dictation, "have to press like the show more", into "have to Proseal UK the show more" (PRSLK both ways, collapsed letters jw 0.778 over the 0.70 multi-word floor). "like" is a preposition and the commonest filler in dictation, and was missing from `_FUNCTION_WORDS`, so the padding rule could not see it. Added there; no name in the live 150-term cache contains it, and "pro seal uk" still corrects to "Proseal UK". The live-corpus test is a moving target because the CRM cache changes between syncs, so each new offender is pinned as a literal (`FunctionWordTests.test_like_is_padding_not_part_of_a_name`).

- `2026-09-23`: **Duplicate words and phrase restarts are collapsed (v1.6.93).** Asked for with real dictations ("if if you can", "it's it's it's", "in the in the CRM"). Three changes to `disfluency.py`, measured on the 200 stored transcripts: 25 change, every edit read and every one a real stutter, with no emphasis or idiom touched. (1) `_DUP_COLLAPSE` widened to words never validly said twice: `if`, wh-words, `just`/`maybe`/`actually`, prepositions like `between`/`through`, object pronouns, `make`/`get`/`want`/`need`/`think`, `more`, and contractions (`it's`, `I've`, `they're`, `don't`). Still excluded on purpose: `that` ("that that report"), `had`, `so`, `like`, `very`, `really`, `yeah`, `no`, `blah`, `dot`. (2) New phrase rule: a 2-4 word phrase repeated exactly and adjacently collapses only when it is visibly unfinished, i.e. it LEADS with a preposition/article/conjunction/wh-word/`if`/`to`/auxiliary, or ENDS on an article/possessive/`to`/`of`/auxiliary. That keeps "I know, I know", "come on, come on", "thank you thank you", "you know you know" and "do it, do it". A phrase with `and`/`or` inside, or an "X and X and X" run, is never collapsed ("on and on and on", "in and out, in and out"). (3) When the dropped copy was lower case, the kept function word loses the capital the engine gave the restart ("also a A thing" → "also a thing"); never for `I` or an acronym, and an all-caps word is never a copy of its lower-case twin ("it IT"). The scan resumes after a collapse instead of restarting (a restart-from-top loop took 1.4s on a pathological 1,500 words, now 9ms). Also runs once more over the WHOLE dictation in app.py before spoken commands: per-chunk streaming meant a double straddling a chunk join ("you | you click") survived. Skipped under Live Typing. **Known limits:** self-repairs with different words ("can could", "could that still then be a… could it still be a") are left alone, since no rule can tell which version was meant without reading context; ✨ Fix All handles those. "in it in it" is also left, because the rule that would catch it also merges "come in, come in". Guarded by `tests/test_destutter.py` (both directions, and the corpus explainer now accepts one copy of an exact repeat).

- `2026-09-29`: **Sound-alike words are picked from the rest of the sentence, before injection (`homophones.py`).** Reported with a side-by-side against Glaido: "Revenue won this quarter" came out as "Revenue one this quarter" while Glaido typed "won". Measured on the stored clip: whisper small.en wrote "Revenue one this quarter." and **Parakeet wrote "Revenue One this quarter."** (a capital, as if a name), so a better engine alone does not fix it. For a true homophone the audio carries no information about the spelling; the engine falls back on its language-model prior, and "one" is far commoner than "won". Echo's LLM `context_fix` could fix it but only OFFERS the fix in the popup after the wrong text is already typed, and an LLM on the stop path is out of scope. New `homophones.fix()`: a local regex pass over the ASSEMBLED dictation in app.py, after the whole-text destutter and before spoken commands (also on the whisper upgrade offer and History Retry, so neither offers "one" back), skipped under Live Typing like destutter, kill switch `config.homophone_fix` (Settings → Fix Sound-Alike Words). Every rule is one pair in one shape and needs evidence on BOTH sides of the word: a left context that makes one spelling grammatical and a right context that rules the other out ("Revenue one this quarter" fires; "phase one this quarter", "I had one the other day", "we lost two customers one this week" do not). Only spaces may sit between the words of a shape; a comma or stop is the speaker's boundary. A capital on the replaced word survives only at a sentence start or in a Title Case phrase ("Closed One" -> "Closed Won"), because Parakeet's mid-sentence "One" was the mistake. Covers one/won (incl. the CRM stage "closed won"), then/than, could of/have, weather/whether, your/you're, its/it's, their/there, to/too, right/write, here/hear, no/know, weak/week and a few fixed phrases. **Validated as a false-positive hunt**: 755,394 words of prose (the Obsidian wiki, both repos' docs) plus 57,062 words of dictated Claude Code prompts change in exactly three places, all correct ("Revenue one/One this quarter" x2, "its the newest one" -> "it's"). About 0.5 ms per dictation. Reports `transcribe_homophone` with rule names only, never the text. Guarded by `tests/test_homophones.py`, which pins every rule's must-not-fire readings next to its fixes.

- `2026-09-29`: **Every install runs the same model, byte for byte.** The download took whatever `resolve/main` served and accepted any file over a minimum size, so a push to the upstream repo (not ours) would have silently changed the model on every new install, and a same-size corrupt file would have loaded. v2 is now fetched from pinned commit `0bbb45a3…` (the model files are unchanged since the 2025-05-06 upload; later commits only touched the README), and each of the four files is pinned to its exact size and SHA-256 (from the HF API; a working install matched all four). `download_model` renames a `.part` into place only after its hash matches, and RESUMES an interrupted `.part` with an HTTP Range request (verified live: HF answered 206 and the resumed file hashed correctly), so a flaky connection makes progress across the retries instead of restarting 650 MB. `verify_model_files()` runs once per file on existing installs (about 0.7 s for 650 MB), deletes a file that does not match so the download replaces it, and records a size+mtime marker (`.verified.json`) so later launches skip the hash (15 ms). v2 stays the default on evidence, not habit: 6.05% average English WER on the Open ASR leaderboard against v3's 6.34% (both model cards); v3 trades English accuracy for 25 languages. An unpinned version (v3) keeps the old size-only check. Proven end to end by simulating a new PC: empty folder to verified model in 58 s, loaded, and the reported clip transcribed. Guarded by `tests/test_model_integrity.py` (pinning, hash rejection, resume, a server that ignores Range, a refused resume, re-verification after a change).
