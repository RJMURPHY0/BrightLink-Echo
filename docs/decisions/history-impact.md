# Decisions: History Impact

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-07-16` — history is per-account with soft deletes, because an unfiltered remote query returned every user's rows.

- `2026-08-06` — "Your impact" cards are click-through (v1.6.47). A headline number nobody can check is decoration, so each card opens a breakdown IN THE SAME SLOT (the three-card row swaps for one full-width panel) and the window grows by the delta while it is open, restoring on close — Home has no ScrollPane and must keep fitting on one page. `_resize` records what it applied and `_on_root_configure` skips saving a size it applied itself, so the temporary height never becomes the account's remembered size. **Time saved** splits dictation vs AI refine with the working shown; **Dictation speed** compares you/typing/handwriting and says what it was measured from; **Day streak** is a month calendar (Monday-start, prev/next month) with a flame on every used day, dates on the rest, a ring on today. Panel heights are per-key (`_impact_panel_height`) because the calendar needs six week rows.

- `2026-08-06` — AI refine now counts towards Time saved (v1.6.47), measured rather than assumed. Only APPLIED refinements count (insert-result or replace — a refine the user looked at and discarded saved nothing). `popup.refine_stats()` returns the wall clock from opening the refine panel to applying the result, plus the instruction word count and whether it was SPOKEN; `stats.refine_saved_seconds` subtracts that from a per-step manual round trip (switch to a chat assistant 4.0s, copy 2.5s, paste 2.0s, TYPE the instruction at `TYPING_WPM`, wait 6.0s, copy back 3.0s, return and paste over 4.5s). Each constant is separate so the panel can show its working. New per-day fields `r`/`rs`/`rp`/`rv` and four `user_daily_stats` columns (`refines`, `refine_seconds`, `refine_prompt_words`, `refine_voice_prompts`) — **re-run `supabase/user_daily_stats.sql`**; until then `_push_day` degrades one column group at a time and everything else still syncs. Guarded by `tests/test_refine_savings.py`.

- `2026-08-06` — Impact breakdowns never resize the window (v1.6.48). v1.6.47 grew the window to fit the panel; the geometry change lands AFTER the atomic present, so it repainted the whole window while the user was looking at one card — the "glitch while transitioning". The panel now replaces the cards row **and** the words bar, sized to `_impact_stack.winfo_height()` captured at open time, so the block is byte-identical in height open or closed and no `_resize` is involved (`tests/test_impact_panel.py::NoResizeContractTests`). Three more flicker sources removed: the open/close swap and `_switch_dash_tab` both run inside `_atomic_ui` (the tab switch previously did a live map/unmap then chased it with repaints at 0ms and 50ms, each a race it could lose); `_atomic_ui` erases ONLY when the window actually moved or resized, because erasing a same-size swap flashes the whole background for a frame; and card hover swaps just the cached background image (`itemconfigure`) instead of re-running the card layout, which did `delete("all")` on every mouse crossing. **A click on the panel body is now inert** — dismiss-on-any-click meant a repeated or bounced click closed the panel the instant it opened, which reads as flicker rather than a toggle; closing is the ✕ or the header strip it sits in (a full-width hit region, since a 12px glyph is a miss waiting to happen). Hit regions are checked in order, so the calendar's month arrows must stay clear of that strip.

- `2026-08-06` — Day streak is a real calendar (v1.6.48): fixed 6×7 grid so the panel height never changes between months, Monday first, leading/trailing days from the neighbouring months drawn in `#383838` for context, today ringed in accent, and a flame on every day dictated — **muted (`#6b4a12`) for out-of-month days**, which keeps a run that spans a month boundary visible without it reading as this month's. Month picker is ‹ / › plus a "Today" link that appears only when you have wandered off; stepping forward past the current month is allowed, because a calendar that refuses to show next month reads as broken. Guarded by `tests/test_impact_panel.py::CalendarGridTests` (every month of 2026-2028 fits the grid, including a 31-day month starting on a Sunday).

- `2026-08-07` — Impact panel dismisses on ANY click (v1.6.51), reversing the v1.6.48 "panel body is inert" rule at Ryan's request: a detail view must never need a hunt for the way out. The **only** exception is a declared hit region — which is now just the calendar's month arrows and its Today link — and those return `"break"`, so the toplevel-wide dismiss handler never sees them. The flicker v1.6.48 was fixing is held off by a 250ms guard (`_IMPACT_CLICK_GUARD`) rather than by making the body inert: the second click of a double-click lands on the panel the first click opened, and closing on that reads as a flicker. The card's own open-click also returns `"break"` for the same reason. Leaving Home closes an open panel (`_switch_dash_tab`), so you never come back to a breakdown you forgot opening. The ✕ lost its hit region (every miss closes anyway).

- `2026-08-07` — Hovering an impact card no longer draws a dark box round its icon (v1.6.51). ui_render bakes the surface colour INTO every glyph (that is how it anti-aliases), so swapping only the card background left the icon carrying `surface` on a `surface_hover` card. `_layout_impact_card` keeps the icon's item id and `_hover_impact_card` re-renders it against the hover surface via the shared `_impact_icon_photo` — still an `itemconfigure` swap, never a relayout. Same-shaped bug elsewhere: none (history rows already re-sync via `_sync_row_image_bg`).

- `2026-08-09` — Time saved shows what the app COST as well as what it saved (v1.6.52): a third row, "Time using it" = total recording seconds + the measured refine-panel seconds, both already netted off the savings above. It fits in the block's fixed height (`_panel_h`, never grows) because each row's explanation was cut to one short line and the row internals tightened — label 10pt→9pt, bar at +11, caption at +20, rows on a computed 42px step. A hairline rule sits above it and its bar is `_PANEL_DIM`, so the spent figure never reads as part of the total. `tests/test_impact_panel.py::TimePanelTests` pins the figure, that nothing overflows the panel, and that **no caption wraps** — a second line pushes the row below it out of the panel.

- `2026-08-13` — Impact figures reconciled and the speed panel re-headed (v1.6.63). The speed card said "5.6× faster than typing" (224/40 wpm, silence excluded) while the time panel implied 3.4× (14 hrs typing vs 4.2 hrs used, wall clock including pauses + refine time). Both numbers were right; they measure different things, and nothing said so. Now `_overall_typing_ratio(snap)` computes the end-to-end multiple ONCE from the same snapshot fields the time panel's rows draw (typing_min ÷ (audio+refine seconds)), the time panel's "Typing by hand" note quotes it ("· 3.4× the time you spent") and the speed panel's footnote reconciles ("Pauses included: 3.4× faster overall"). The 5.6× stays as the speech-rate multiple: it sits directly above the 224/40 rows it is computed from. Layout: the speed figure now rides the panel header ("224 wpm" + "dictation speed" caption via `_panel_head`, same shape as the time panel) and the speech multiple takes the line the figure occupied. Footnote must stay within two lines: a third clips at the panel's bottom edge at the app's real ~408px canvas width (caught by screenshot, pinned in `tests/test_impact_panel.py::SpeedPanelTests`, which also pins that both panels quote the same end-to-end figure).

- `2026-08-18` — "Your impact" dropdown scopes ALL three cards, not just the words line (v1.6.70). Reported: picking "This week" should give time-saved / dictation-speed / day-streak for the week, and clicking a card should drill into that period. Previously the three cards always showed lifetime and only the footer words count followed the range. `StatsStore.snapshot(rng)` now scopes the aggregates to today/week (Mon-start)/month/year/all in a single pass; **rng='all' is byte-identical to the old lifetime behaviour** (the window then spans every day and folds in the collapsed `carry`), so every existing caller/test is unaffected. The streak card is inherently a running lifetime concept, so 'all' shows the true streak while a bounded window shows days-active-within-it ("5 days · active this week"); its calendar breakdown stays the whole navigable picture. Dictation speed falls back to the LIFETIME measured rate for a thin window (a single day rarely clears the 50-word bar) rather than dropping to the nominal 160, and the speed panel's explainer names its source (window / lifetime / nominal) so the number and its working never contradict. Default range changed `today`→`all` so a fresh install still opens on the impressive lifetime figure. Guarded by `tests/test_impact_range.py` (window scoping + carry + fallback) and the existing impact-panel/speed tests.

- `2026-09-09` — **"Your impact" takes an explicit from/to span (v1.6.75).** The five named windows do not answer "how did the first week of last month go", so the range control is now `RangePicker`, a **subclass** of `Dropdown` with a second tab: two dd/mm/yyyy fields (real Entries, so a span can be typed as well as clicked) plus a Monday-start month calendar, Clear and Apply. Subclassed, never forked — the closed-control paint, the permanent dismiss-anywhere binding and the lose-foreground watch each took a release to get right. Two clicks make a span; a click before the start restarts it rather than inverting it; Apply with one date is a single day. The key is `custom:YYYY-MM-DD:YYYY-MM-DD`, parsed by `config.parse_custom_range` (the one place the format is defined — `config.load()` and `stats.snapshot()` both call it), and it behaves as a sixth **bounded** window: it scopes time-saved / speed / streak / words exactly like the named ones and, like them, EXCLUDES the collapsed `carry` total, which only an unbounded window may fold in. Panel captions read "saved in 1 Sep – 9 Sep" via `_range_phrase`. Tab switching resizes the panel and then erase-repaints it, because resizing a mapped `overrideredirect` window blits the old pixels into the new position and `RDW_UPDATENOW` only validates Tk's update region (the `_atomic_ui` / `popup._reposition` lesson again). **Dropdown option labels must stay short** — the control sizes itself to its widest option, and the first draft of the sentence-endings labels overflowed the card it sits in. Guarded by `tests/test_range_picker.py`.

- `2026-09-14`: **The Your impact range picker opens one way (v1.6.79).** Reported with screenshots: Periods opened one way, From / to another, and switching From / to → Periods left the short list floating where the tall panel's top had been. Two causes in `RangePicker`: the side (below, else above) was chosen from the height of whichever tab was open, and `_set_tab` kept the panel's top-left and only changed its height. Now `_opens_above()` decides once per open from the TALLEST tab, preferring the side with more room inside the app window (the control sits at the bottom of Home, so it rises over the app), with the monitor as the tiebreak when the tallest tab cannot fit on that side. `_panel_xy()` keeps the edge next to the control glued to it, and `open()` and `_set_tab()` both place through it. Base `Dropdown` placement is unchanged. Guarded by `tests/test_range_picker.py::PlacementTests`, which includes a real open → From / to → Periods cycle asserting the bottom edge never moves.

- `2026-09-25`: **The From / to calendar fills all six rows (v1.6.94).** The grid stays a fixed 6×7 so the panel never changes height between months (it is anchored by the edge next to the control, so a moving far edge would slide the month arrows out from under the pointer), but a five-row month left a whole empty row above Clear / Apply. The neighbouring months' days now fill the grid, dimmed (`RangePicker._OTHER_MONTH`) and still pickable, the same shape as the Day streak calendar; the footer band went 46 → 38px (`_FOOT_H`). Guarded by `tests/test_range_picker.py::PickerTests::test_every_grid_row_is_filled`.

- `2026-09-25`: **History rows carry a "Send feedback" flag (v1.6.95).** Asked for after Glaido's "Report to improve model". On row hover a PIL `flag` glyph appears left of the bin (zone `width-96 … width-66`, header only, hidden while the delete confirm shows; the preview text now stops at `width-164` so it never runs under it), warms to the accent on the pointer and, after HelpDot's 220ms, shows "Send feedback" (or "Sign in to send feedback" when signed out, where a click does nothing). The tooltip is now ONE implementation, `_HoverTip`, shared with HelpDot. Clicking opens a card PLACED over the dashboard (never a Toplevel): what Echo heard (read-only), **What it should have said** prefilled with the transcript so the user fixes only the wrong words (an exact correction pair beats a blank "describe it" box), an **Include the recording** tick (ticked, hidden when the WAV is not on this device), Cancel / Send feedback. Send is live only once the correction differs from what was heard. `SupabaseLogger.send_feedback` uploads the WAV to the private `echo-feedback-audio` bucket under `<uid>/` and inserts an `echo_feedback` row; an upload failure still files the row without audio, and a failed insert keeps what the user typed. Provenance: each LOCAL history record is now stamped with `engine`/`model`/`language`/`app_version` at dictation time (`app._engine_meta`, `log_transcription(meta=)`, read back by `local_meta(created_at)`); the remote `transcriptions` payload is unchanged. Older rows report the currently configured engine with `engine_source: "config"`. The table, bucket and RLS live in the BrightLink repo (`supabase/migrations/20260925120000_echo_feedback.sql`, insert-own, super admin reads via `is_super_admin()`), and reports show in BrightLink under Feedback Reports → Echo. Until that migration is applied every send reports "Couldn't send. Try again." Guarded by `tests/test_history_feedback.py`.

- `2026-09-25`: **Range picker opens the way its arrow points, with its tabs next to the control, and new windows (v1.6.97).** On Ryan's screen the window sits low, so the picker still rises above the bar (kept on purpose), but its chevron pointed down and its tabs sat on the far (top) edge. Because the edge next to the control is the one glued to it, a tab switch changed the height and moved the tab row out from under the pointer. Now `_paint_panel` draws the tabs on the edge nearest the control (bottom when `_menu_above`) and shifts the content by `_dy`, so the tabs never move on a switch; `RangePicker._chevron_up()` points the arrow the way the panel opens (or will open, when closed) via a `Dropdown._chevron_up` hook that is always False for the base class. The list is Today, Yesterday, This week, This month, Last 6 months, Last 12 months, All time: "Last 12 months" rather than "Last year", which reads as the previous calendar year. Both rolling windows run up to and including today. Every named window is defined once in `config.named_range_bounds()`, used by both `stats.snapshot()` and `_words_by_range`. `"year"` stays a valid key (old saves, tests) but a saved "year" opens as Last 12 months. Guarded by `tests/test_range_picker.py::OpenAboveLayoutTests` and `NamedWindowTests`.

- `2026-09-25`: **The range picker opens inside the window, and the feedback dialog plays the recording (v1.6.98).** Reported with screenshots: the From / to panel was still showing over the Hotkey tab, and it hung past the bottom of the app over whatever was behind it. The floating `-topmost` Toplevel is gone. `RangePicker` now takes `panel=` (a canvas in the impact section) and `on_toggle(show, paint)`, and `AppWindow._toggle_range_panel` swaps that canvas in for the words bar + cards at the height they had, inside `_atomic_ui`, the same slot and rule as the impact breakdowns: the window never resizes and nothing below moves. As a child of the page it cannot leave the window, and `_switch_dash_tab` calls `Dropdown.close_all()` (a weak registry of every live Dropdown), so no list of any kind survives a page change. The panel hides the control that opened it, so it has its own ✕, Escape, and closes on any click outside it; clicks in its date fields are told apart by widget ancestry, never by an Entry returning "break" (that would stop the caret landing). Layout fits the ~200px section: Periods in two columns; From / to with the fields, a "N days" line and Clear / Apply on the left and the six-row calendar on the right, its row height taken from the section. The old side-choosing code (`_opens_above`, `_panel_xy`, tabs-on-the-near-edge) went with the Toplevel. **Feedback dialog:** the recording is playable right under "What Echo heard" (`_build_feedback_player`: the History row's play/stop button, peak waveform that fills as it plays, elapsed / total), since it is the evidence the correction is checked against. Same winsound as History, so starting one stops the other; closing the dialog stops playback. Guarded by `tests/test_range_picker.py::InWindowTests` / `TabSwitchTests` and `tests/test_history_feedback.py::DialogTests`.

- `2026-09-28`: **From / to calendar: calendar on the left, fields on the right, this month only** (Ryan's call, reverses the v1.6.94 filled grid). The v1.6.94 reason for a fixed 6×7 grid (a floating panel whose far edge moved) went with v1.6.98's in-window panel, whose height is fixed by the section. `_paint_custom` now draws only the month's own days; the grid has just the weeks the month spans (`_grid_rows`, 4 to 6) and they share the section height (`_cell_h(rows)`, capped at 28). `_custom_columns` returns (fields x0, x1, calendar x0, x1) with the fields column (`_FIELD_W`) pinned right. Guarded by `tests/test_range_picker.py` (only-this-month, rows per month, calendar-left, fits for a 6-week and a 4-week month).

- `2026-10-05`: **BrightLink CRM rows in History show the CRM's live favicon.** A dictation into a browser tab the CRM titled ("Contacts | BrightLink", so the captured `app_name` is `brand.CRM_NAME`) showed Chrome's icon, because the curated brand pack had no BrightLink entry and the exe is the browser. `app_icons.get_site_icon` now runs first in `_history_icon`: for a browser row named exactly `CRM_NAME` it reads `brand.CRM_URL`, takes the page's `<link rel="icon">` href and saves that image to `%LOCALAPPDATA%\FTC Whisper\icons\crm-favicon.png` on a daemon thread (every 6h, 15 min after a failure, last good file kept). So a new CRM favicon reaches Echo with no release. Until the first download lands the bundled `assets/brand/brightlink-mark.png` stands in. Any other page, including a Google search for BrightLink, keeps the browser's icon. Echo cannot read the address bar, so the tab title is the test: a non-BrightLink page whose title ends in "BrightLink" would also match. Superseded favicon PhotoImages stay cached (freeing one a drawn row still shows blanks it). Guarded by `tests/test_app_icons.py::CrmFaviconTests`.
