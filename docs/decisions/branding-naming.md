# Decisions: Branding Naming

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-09-17`: **Renamed to BrightLink Echo with every name in one file, and signing moved to Azure Artifact Signing (ships in the next release).** The company is registered (BRIGHTLINK (OS) LTD, company 17459281, incorporated 2026-09-15), which unlocks code signing. `brand.py` holds two kinds of name. DISPLAY names (`PRODUCT_NAME`, `COMPANY_NAME`, `WEBSITE_URL`, `DOWNLOAD_ASSET`) drive everything a person sees: titles, tray, notifications, the Google sign-in page, shortcut names, the Installed apps entry and the exe's version resource (the spec renders `version_info.txt` with names from `brand.py`; the version numbers are untouched, so the release step is unchanged). FROZEN identifiers keep their FTC Whisper values for good: the data folders (660 MB model, session, history), the canonical exe `FTC Whisper.exe` (taskbar pins point at it), the mutex, the logon task, the Run value, `ftcwhisper://` (the CRM opens `ftcwhisper://launch`), the uninstall key, the repo, and the `FTC-Whisper.exe` update asset (every installed updater and the CRM's download button fetch it). A plain find-and-replace would have broken uninstall: `app_install.APP_NAME` doubled as the folder name, the `safe_to_delete` guard, the taskkill image and the Run value, so a renamed build would have targeted a folder that does not exist and left the running exe locked. Existing installs switch on their normal auto-update. `app_install.rename_shortcuts` renames an old-named Start-menu or desktop shortcut in place: it never creates one, never deletes the current one, and treats a case-only change as a rename. The Installed apps entry is rewritten when the name or publisher differ, not only on a version change. `_announce_update_if_any` sends ONE notice ("FTC Whisper is now BrightLink Echo"), keyed by `last-product-name.txt`, so any future rename gets it free. Known limit: a pinned taskbar or Start tile may keep the old name or need re-pinning, because Windows owns pins. CI publishes the one signed build twice: `BrightLink-Echo.exe` for downloads, `FTC-Whisper.exe` for the update channel. Signing facts, checked on Microsoft Learn: Trusted Signing was renamed Artifact Signing; UK organisations qualify with no minimum company age (a Microsoft employee, August 2026); individuals only in the US or Canada; validation takes 1 to 20 business days, portal only; free and trial subscriptions are refused. The workflow logs in with GitHub OIDC (federated credential on the `release` environment, `allow-no-subscriptions`), so no client secret exists. Five repo variables configure it; a partial set fails the build; `REQUIRE_SIGNING=true`, set once signing is proven, refuses unsigned builds. `workflow_dispatch` became a dry run unless `publish` is ticked, because dispatch always builds and `overwrite_files` + `make_latest` would otherwise replace the live release's assets with a test build. Signed apps still get a softer SmartScreen prompt until reputation builds over weeks. That reputation follows the company on the certificate, so renaming the app later costs nothing. Guarded by `tests/test_brand.py` and `tests/test_app_install.py`.

- `2026-09-21`: **BrightLink | Echo artwork everywhere a logo shows (v1.6.81).** `assets/brand/` holds the CRM's own files (`favicon.png` as the chain mark, `link/wordmark-on-dark.png`) plus Ryan's Echo wordmark and chain+Echo badge; `logo_cache.py` composes everything from them and the spec refuses to build without them. Header, "Signing you in…" splash and sign-in show the lockup (BrightLink wordmark, hairline divider, Echo) at 42px, both words on one baseline with Echo's caps 1.1x BrightLink's; at 46px Echo sat against the gear and read as part of it. The gear moved to `place()` so the lockup centres on the WINDOW (packed beside the gear it centred in the space left of it). The post-dictation badge shows chain + Echo. Window title is `brand.WINDOW_TITLE` ("BrightLink - Echo", Ryan's call); shortcuts, Installed apps and the exe keep `PRODUCT_NAME`. **App icon** (`logo.ico` = running window, `exe_icon.ico` = embedded, both from `logo_cache.write_icon`, as is the History self-icon `assets/brand_icons/ftcwhisper.png`): the chain OVER "Echo" on a dark rounded tile. Stacked, not side by side like the badge, because in a square side by side leaves "Echo" ~4px tall at taskbar size; below 24px the frame is the chain alone (the title bar's 16px, beside a title that already says Echo). Pinned taskbar tiles keep Windows' cached icon until re-pinned. Guarded by `tests/test_brand_artwork.py`.

- `2026-09-22`: **The CRM's Download button fetches `BrightLink-Echo.exe`** (Brightlink `src/components/AppSidebar.tsx`, `downloadWhisperLatest`). It still fetched `FTC-Whisper.exe`, so a new user's file landed as "FTC-Whisper.exe" in the browser's downloads. The filename is the release asset's name, and GitHub turns spaces in asset names into dots, so "BrightLink - Echo.exe" is not available; `BrightLink-Echo.exe` is the closest. `FTC-Whisper.exe` stays published for every installed updater: the CRM no longer using it changes nothing about that invariant. The downloaded exe already carries the Echo icon and "BrightLink Echo" version resource; the plain icon a browser shows mid-download is its own placeholder until the file completes.

- `2026-09-22`: **Repo renamed `RJMURPHY0/FTC_Whisper` → `RJMURPHY0/BrightLink-Echo`** (Ryan, on GitHub). Checked before touching code: the old API URL answers 301 to the repo id, and the real `updater.get_latest_release()` on v1.6.86 source still returned v1.6.86 with the new-repo download URL and its SHA-256, so installed copies keep updating. `brand.GITHUB_REPO` moved to the new name, so builds from the next release onwards do not depend on the redirect; the release after that moves the fleet off it. The Azure federated credential must name the new repo (GitHub puts the current name in the OIDC subject). The CRM's version check and Download button use the new name too.

- `2026-09-24`: **Notifications are titled "BrightLink Echo", not "FTC.Whisper".** Reported by a user on v1.6.89 with a screenshot of the update toast. The app sets the AppUserModelID `FTC.Whisper` (now `brand.APP_USER_MODEL_ID`, frozen: taskbar grouping and pins hang off it), and Windows titles a toast from an unpackaged app with that raw id unless the id has a name registered. `app_install.register_notification_identity()` writes `HKCU\Software\Classes\AppUserModelId\FTC.Whisper` (`DisplayName` = `PRODUCT_NAME`, `IconUri` = `%LOCALAPPDATA%\FTC Whisper
otification-icon.png`, rendered once from `logo_cache.app_icon_image`), called from `AppWindow.run` right after the id is set and before any toast can fire, rewritten every launch so a future rename reaches existing installs. Uninstall removes the key. Verified live with a non-Store Python (a Store Python shows its own package name instead, so it cannot test this): the toast read "BrightLink Echo" with the Echo icon. Windows caches the name per id, so it can lag one notification on a machine that already showed the old one. The source folder was also renamed `FTC -whisper - transcription` -> `BrightLink - Echo` the same day; nothing in the repo held the absolute path. Guarded by `tests/test_app_install.py::NotificationIdentityTests`.

- `2026-09-30`: **The on-disk names moved to BrightLink Echo (v1.8.1), reversing the 2026-09-17 "frozen for good" call.** Installing on a colleague's laptop showed `%LOCALAPPDATA%\FTC Whisper\...` in the installer, and Ryan wants no person to see the old name anywhere: folders, exe (Task Manager), Startup apps, Installed apps key, shortcuts, temp files. Moved: data folders (`%LOCALAPPDATA%` and `%APPDATA%\BrightLink Echo`), exe `BrightLink Echo.exe`, mutex, logon task, Run value, uninstall key `BrightLinkEcho`, URL scheme `brightlinkecho`, setup mutex, user agents, temp names (`brand.FILE_SLUG`). Kept, because older copies find them by name: `FTC-Whisper.exe` (the bridge), `FTC-Whisper-Setup.exe` and `FTC-Whisper-rollout.json` (v1.8.0 copies), `ftcwhisper://` (the CRM; registered beside the new scheme to the same exe), AppUserModelId `FTC.Whisper` (changing it splits every taskbar pin; its display name already reads BrightLink Echo), the signer. The old values live on in brand.py's LEGACY block. **How machines move:** only `installer/activate.ps1` moves folders, because it is the one place the app is stopped and new code runs. It leaves the current directory first (v1.8.0 starts it inside the legacy folder, and a process's current directory cannot be renamed), renames the whole legacy folder (or moves each item the new one lacks), does the same for `%APPDATA%`, renames the legacy exe to the current name so the normal swap keeps it as `.previous`, and writes `migrated.json`. Every move is recorded; any failure (locked file: exit 6, no bad-version so the updater retries; crash at start: exit 5 with bad-version in the legacy folder; failed registration: exit 4) moves everything back and removes what the new version registered. **Reaching v1.8.0 copies:** they stage with `/STAGEONLY` and no `/DIR` and check `pending-<v>\FTC Whisper.exe`, so the installer stages in the legacy folder for exactly that call and writes the exe under both names; every newer updater passes `/DIR`. **Pre-1.8 copies** stay in the legacy folder on the onefile bridge (its unpack folder is the legacy one) until the rollout moves them through the installer, which then migrates them too. `data_paths.py` is the single resolver: legacy folders until the machine is marked migrated. On each launch, once per exe path, `app_install.register` removes the legacy uninstall key, task and Run value and retargets desktop, Start menu and taskbar/Start pins aimed at the legacy exe. Proven by `tests/test_activation.py` MigrationTests (real script, fake profile folders: whole move, crash rollback, locked-file undo then retry, install over a legacy folder, failed install gives it back) and the e2e `installed` scenario (real v1.8.0 from GitHub updating itself).

- `2026-10-01`: **Start with Windows crosses the rename with its Task Manager switch.** Merged with the two-launcher Start with Windows (`release-updater.md`, 2026-10-01): the Run entry and its `Explorer\StartupApproved\Run` record now carry the current `RUN_VALUE_NAME`, and `brand.LEGACY_RUN_VALUE_NAME` names the old pair. A disable made in Task Manager under the legacy name holds after the move: `activate.ps1`'s sign-in bridge (written when the legacy task or Run value exists) now passes `--startup` and copies the legacy StartupApproved record to the new name; and `app._task_manager_startup_state()` reads the legacy record when the current name has no Run entry yet, so `_startup_setting_at_launch()` (and `--install` with no installer tick) keeps Start with Windows off. It is read on the main thread before `app_install.register` runs, whose `remove_legacy_launchers()` then deletes the legacy task, Run value and StartupApproved record. A rolled-back migration removes the new Run value and record too. Uninstall removes both pairs and both tasks. Only a disable carries over: a legacy entry that is on does not override a saved Off. An installer tick passed with `--start-with-windows` still wins, as it does for the current name. Tests: `LegacyStartupCarryOverTests` in `tests/test_store_install.py` (fake winreg).
