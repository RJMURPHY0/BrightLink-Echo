# Decisions: Cloud Sync

Started 2026-09-29. Add new decisions as a dated entry at the bottom.

- `2026-09-29`: **Cloud Sync is opt-in, off by default on every PC, and carries everything personal (v1.7.4).** Ryan asked for "a very clear and simple option… automatically turned off by default… to store all of your stuff over the cloud so moving between devices is easier… opt in and opt out". Until now part of this ran for **every signed-in user with no switch**: every dictation's text went to `transcriptions`, applied refinements too, vocabulary and snippets went to `user_vocabulary` / `user_snippets`, and History pulled other PCs' rows back down. PRIVACY.md and the Store listing even promised it. Decisions, each Ryan's call:
  1. **Everyone starts off, existing users included.** The flag is `config.cloud_sync` (default False, per PC), handed to `SupabaseLogger.set_sync_enabled`. Every personal remote path is gated on it: `log_transcription` / `log_refinement` / `update_transcription` remote writes, `refresh_history` pulls, the tombstone purge, and `push_library` / `fetch_library`. Existing users therefore lose cross-device history until they opt in. That is the accepted cost of private-by-default.
  2. **When on, "pretty much everything" syncs.** That covers history text (local rows the cloud lacks are uploaded, and the newest 200 cloud rows are written into `history.json`), recordings (new private bucket `echo-sync-audio/<uid>/<canonical_key>.wav`), vocabulary and snippets (existing merge), learned phrases, and preferences (both as one `echo_user_state` jsonb row each).
     - The settings merge is per key, and the newer change wins. `config.sync_stamps` records when each synced setting last changed on this PC. With no stamp on either side, a chosen value beats the default, so an old PC's customisations from before Cloud Sync existed still travel.
     - `SYNCED_SETTINGS` lists preferences only. The mic, hotkeys, popup geometry, start-with-Windows, engine/model and keys are this machine's.
     - Phrase counts merge by max. A forgotten phrase is remembered (`PhraseStore._forgotten`), so another PC cannot hand it back unless it was learned again afterwards.
  3. **Turning it off offers to delete** what is in the cloud: an inline confirm in the card, and a standing "Delete my data from the cloud" link whenever sync is off and someone is signed in. The link matters because existing users' pre-1.7.4 data is still up there.
     - `delete_cloud_data` removes transcriptions, vocabulary, snippets, `echo_user_state` and the recordings.
     - It reads each table back to confirm the rows are gone, because an RLS-refused delete does not raise. Any part that failed is named in the status line.
  4. **Usage counts stay outside Cloud Sync.** `user_daily_stats` holds words, seconds and refines, never text, and BrightLink's Home dashboards (progress, value, view-as-person) read it for every signed-in user. It keeps flowing for signed-in users regardless of the switch, and "delete my data" leaves it alone.
- **Found on the way:** three quality guards (hallucination, prompt echo and stutter) attached up to 200 characters of the dictation to `error_events`, contradicting PRIVACY.md's "never includes what you said". The reporter wiring in app.py now drops `sample` / `text` / `excerpt` unless Cloud Sync is on.
- **Known consequence:** the super-admin activity feed (`sa_product_rows`, BrightLink repo) builds its "echo.dictated" entries from `transcriptions`. Those now appear only for users with Cloud Sync on. The Home figures are unaffected (item 4).
- **Recordings:** each clip is named `audio_store.canonical_key(created_at)`, UTC `YYYYMMDDHHMMSSffffff`, not the raw digits. Postgres returns the same instant written differently (`.8432` vs `.843200`, `Z` vs `+00:00`), and the name must agree between the PC that recorded it and the PC reading the row back. A new clip uploads as its dictation finishes. A full sync uploads what is missing and downloads the clips of this PC's history rows it does not hold, then prunes to the local caps.
- **Database:** `supabase/cloud_sync.sql` is a copy of BrightLink migration `20260929210000_echo_cloud_sync.sql`, applied by that repo's workflow. It creates `echo_user_state` (owner-only), the `echo-sync-audio` bucket (owner read/write/delete, not even the super admin reads it), and owner UPDATE/DELETE on `transcriptions`. Every sync step tolerates the table or bucket being missing.
- **When it runs:** at sign-in (`CloudSync.start`), when the switch goes on, every 15 minutes while on, and per dictation for the recording. A changed synced preference is pushed 3 s later, debounced.
- **Pinned by** `tests/test_cloud_sync.py` (33 tests, default-off first). The existing remote-path tests in `test_supabase_history.py` / `test_history_feedback.py` now turn sync on explicitly.
