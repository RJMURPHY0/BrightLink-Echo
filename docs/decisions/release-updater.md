# Decisions: Release Updater

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-04-16` — release asset renamed to exactly `FTC-Whisper.exe` because the auto-updater matches that literal filename on `releases/latest`; the old name broke auto-start and auto-update on installed clients.

- `2026-07-08` — updates made fully automatic because users never checked for them manually.

- `2026-07-10` — code signing via **Azure Trusted Signing** in CI because unsigned hand-built exes get flagged by SmartScreen/AV. Requires six repo secrets (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_ENDPOINT`, `AZURE_CODE_SIGNING_NAME`, `AZURE_CERT_PROFILE_NAME`) plus one-time Azure setup — see `docs/CODE_SIGNING.md`. Signing is skipped, not failed, when secrets are absent. **Superseded 2026-09-17:** Azure Artifact Signing over GitHub OIDC, five repo variables and no secrets (see that entry). The six secrets were never set, so every release up to v1.6.80 shipped unsigned.

- `2026-07-13` — CI auto-releases on `APP_VERSION` bump because the updater checks GitHub **Releases**, not commits; before this, pushing to `main` shipped nothing the app could see and it kept reporting "up to date".

- `2026-08-05` — The app registers itself as a real Windows application (v1.6.46, `app_install.py`). Downloading the exe previously produced a loose file: no Start-menu entry, nothing in Windows Search, nothing in Settings → Apps. Now first run also writes a **Start-menu shortcut**, a **desktop shortcut (once)**, an **HKCU Add/Remove Programs entry** (DisplayName/Version/Publisher/Icon/EstimatedSize/UninstallString) and an **App Paths** key. Deliberately NOT a real installer (Inno/MSI): the updater swaps the exe in place at `%LOCALAPPDATA%\FTC Whisper\FTC Whisper.exe`, and an installer would fight that. This is the per-user shape Slack/Discord/Teams/VS Code-user-setup ship. Every shortcut and registry value points at the CANONICAL exe, so auto-update cannot stale them; `register()` re-runs each launch and refreshes DisplayVersion. Uninstall is `"<exe>" --uninstall [/S]`, handled at the TOP of `_main()` before the version handoff and the single-instance mutex (the resident copy would otherwise kill the uninstaller), and it defers the folder delete to a PowerShell script guarded by `safe_to_delete()` — only `%LOCALAPPDATA%\FTC Whisper` and `%APPDATA%\FTC Whisper`, never a computed parent. The desktop shortcut is created once and never resurrected if the user deletes it. Windows has had no API to pin to Start since 1703, so Start-menu + desktop is the ceiling; pinning stays the user's call. Guarded by `tests/test_app_install.py`.

- `2026-09-14`: **Outage: v1.6.79 transcribed nothing after auto-update, fixed in v1.6.80.** Every dictation came back "No speech detected" with nothing injected and nothing in history. The v1.6.79 code was NOT the cause. Root cause, proven step by step: (1) a PyInstaller onefile Python process carries its bootloader's `_PYI_APPLICATION_HOME_DIR` / `_PYI_ARCHIVE_FILE` / `_PYI_PARENT_PROCESS_LEVEL` in `os.environ`; (2) the updater's swap script was spawned with that environment and `Start-Process` passed it to the new exe; (3) the new exe, at the SAME path, read the variables, took itself for the old bootloader's child, skipped unpacking and ran on the OLD `_MEI` folder (on Ryan's machine the running v1.6.79 process loaded every DLL from v1.6.78's 12:04 unpack); (4) CI had silently taken onnxruntime 1.30.0 (requirements.txt has only `>=` floors), so v1.6.79's onnxruntime 1.30 Python layer ran on v1.6.78's 1.29 binary, and every `InferenceSession.run` raised `no attribute 'is_webgpu_graph_capture_enabled'`. `_recognize` swallows that and returns "", and the Silero gate disables itself on the same error. Reproduced exactly in a venv (1.30 `.py` over 1.29 binaries: model "loads", every transcription is ""), and the bootloader behaviour was reproduced on a minimal onefile exe built with PyInstaller 6.22.2 (inherited env: child reuses the parent's `_MEI`; `PYINSTALLER_RESET_ENVIRONMENT=1`: fresh `_MEI`). Every earlier in-place update had the same flaw and survived only because consecutive builds bundled identical libraries. Fixes: `pyi_runtime.clean_launch_env()` on every launch of our own exe (updater swap script, stale-copy handoff); `pyi_runtime.relaunch_if_foreign_runtime()` at the top of app.py, before any project import, which relaunches once with a clean environment when the process's parent is not its own bootloader (this is what rescues an install being updated BY a build whose updater still leaks the environment, i.e. every v1.6.79 install); `constraints.txt` pins all 68 packages (PyInstaller included) to the v1.6.78 build and CI installs with `-c constraints.txt`; and `FTC Whisper.exe --selftest <wav> <report.json>` loads the real model through the bundle's onnxruntime and transcribes one file, so a packaged build can be proven without a microphone. **The PyInstaller pin is 6.22.3, not v1.6.78's 6.22.2, and that is load-bearing**: every install still on v1.6.78/v1.6.79 applies v1.6.80 with its OLD leaky swap script, and a 6.22.2 bootloader answers that launch with "Security validation failure: parent process has different executable!" (app never starts), while 6.22.3 inherits the old unpack and lets `pyi_runtime` relaunch clean (bootloader source read: 6.22.3 verifies the parent only when elevated). The old launcher is killed mid-cleanup by that swap script, so the inherited folder may be partly deleted; the bootloader deletes in NTFS order, which starts with `anthropic/` (~1,400 files), while `base_library.zip` is ~#1,600 and `python311.dll` ~#4,500. Proven end to end on the real build with the swap script's exact wait/kill/sleep/relaunch sequence, 3 of 3 passes (0, 626 and 0 files deleted before the kill; each relaunch logged "Relaunched on own runtime" and transcribed). A synthetic payload that put `base_library.zip` first failed every time with "Failed to start embedded python interpreter!", so do not add bundle contents that sort before `anthropic` and are needed at startup. Also learned the hard way: `uv` installs by HARD LINK from its cache, so editing a file in one venv edits the cache and every venv built from it; use `--link-mode copy` for any venv you modify. Guarded by `tests/test_pyi_runtime.py`. Rollback point if ever needed: v1.6.78, commit `832a0de`, shipped as a NEW higher version with `constraints.txt` kept (and PyInstaller 6.22.3).

- `2026-09-21`: **An update can no longer install a half-written exe (v1.6.82).** Ryan's v1.6.80 -> v1.6.81 update left `FTC Whisper.exe` as the first 21,299,200 bytes of the 129,595,787-byte release (byte-identical prefix, an exact multiple of the 64 KB download chunk), and it would not start: "Could not load PyInstaller's embedded PKG archive". The download itself had been complete and size-verified at 18:27:39. Every update entry point (the automatic updater, Settings' Update Now, the CRM's `/update`) ran its OWN `run_auto_update`/download, each guarded only against itself, and the automatic and manual flows shared ONE file, `FTC-Whisper-new.exe`. A second run deleted the verified file and began re-downloading into it; the first run's idle wait ended, `apply_update` `os._exit`ed the process mid-download, and the swap script's `Copy-Item` copied the partial file and logged "Copy succeeded" (the installed exe's mtime, 18:29:29, is the partial file's, earlier than the swap itself). Fixes, each pinned against the real code in `tests/test_update_integrity.py`: (1) **one run per process**: a second caller joins the run in flight and may only ask it to install now (`apply_now` cuts the idle wait), it never downloads; Update Now and `/update` both go through it; (2) **a download file per run** (`FTC-Whisper-new-<pid>-<time>.exe`; leftovers over an hour old are swept, younger ones may be another run's); (3) **GitHub's own SHA-256** (the release API's asset `digest`) is enforced on download, and the file is re-hashed right before install; (4) **the swap script installs only a file that still has the verified hash**, via a staged copy it also hashes, swapped in with `File.Replace` (old exe kept as `.previous` and restored if the installed hash is wrong); anything else leaves the installed exe untouched and relaunches it; (5) `pyi_archive_intact()` checks the PyInstaller archive marker at the end of the file (a cut-off exe keeps its version resource, so a version check cannot see the damage): `verify_exe` requires it, `_handoff_to_canonical_if_newer` never hands off to a broken install, and `_ensure_installed_copy` repairs one from any whole copy that runs, so **a user stuck on the error recovers by downloading the install link and running it once**. The real PowerShell script is executed in the tests against dummy files (good install; download cut short after verification refused; no hash refused) and parsed as shipped, which caught a `$$false` that would have stopped every update installing. NB this protects updates FROM v1.6.82 on: each install's CURRENT version runs the swap, so v1.6.80/81 clients take v1.6.82 through the old script, and the race needs Update Now clicked during the idle wait (or two instances) to bite.

- `2026-09-28`: **Microsoft Store groundwork (v1.7.1).** The Store takes the existing signed exe by versioned URL (policy 10.2.9), which requires a silent install and lets the app keep self-updating (10.2.5 exempts 10.2.9 products). MSIX rejected: its container would fight the in-place updater, the canonical exe path, the logon task and the model folder. New `--install /S` (`_run_silent_install`) installs the canonical copy, registers Start menu, Installed apps, URL protocol and the logon task, and exits with no UI; it runs in `_main` next to `--uninstall`, before the handoff and the mutex, so it works while the app is open. `_ensure_installed_copy` now keeps an intact installed copy when refreshing it fails (the running exe is locked), because falling back to the current path registered the Store's temporary download as the Start-menu and boot target. Start at sign-in is now consent-gated (policy 10.2.8) by `config.start_with_windows` (default on, Settings toggle; off deletes the logon task). The old `auto_start` key is deliberately left unread: every existing config holds `false` there. Echo's privacy policy is `PRIVACY.md` (BRIGHTLINK (OS) LTD; the CRM's /privacy names FTC Safety Ltd and does not cover Echo). Partner Center values, listing copy and certification notes: `docs/MICROSOFT_STORE.md`. Guarded by `tests/test_store_install.py`.
