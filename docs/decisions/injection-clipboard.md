# Decisions: Injection Clipboard

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-07-23` — Injection reliability: capture the focused CHILD control + caret at record start (`_capture_focus_target` via `GetGUIThreadInfo`, race-free on the synchronous hotkey thread), not just the top-level hwnd. Final `inject()` takes `target_hwnd`/`target_child`: the clipboard paste REFUSES Ctrl+V when the live foreground is not the target (so a mid-speech click elsewhere can't paste into the wrong window), and native `_post_wm_char` posts straight to the stored control (needs no foreground) so the text still lands in the box the user originally clicked. `_focus_window` now polls up to 300ms for the foreground switch and restores child focus cross-thread; the browser DOM-focus click uses the captured caret, not the stale mouse position. Root cause of "cursor stays, text never appears" was: only the top-level window was captured, `_focus_window`'s fallback fabricated success, and `_clipboard_paste` returned True purely on `SendInput`-sent — so a lost foreground pasted into whatever the user clicked (or nowhere) while reporting success. Guarded by `tests/test_inject_target.py`; proven on real Win32 EDIT controls. Streaming/live-typing focus contract untouched (only `inject()` sets the targets). Also: `show_popup` toggle (default on) suppresses the post-dictation popup but still shows it if injection failed; `trim_silence` (default on) skips storing committed chunks that transcribed to no words. NB: dictation audio is LOCAL (`%APPDATA%\FTC Whisper\audio`), never uploaded to Supabase (sole exceptions, both opt-in per clip: voice training, and a History feedback report sent with "Include the recording" ticked, 2026-09-25) — Supabase only ever stores the transcript text row, so silence-trim saves LOCAL disk only.

- `2026-08-07` — Copy to Clipboard OFF now actually means off (v1.6.51). A clipboard-paste injection backs up the clipboard and restores it 1.5s later, but with **nothing to restore** (empty clipboard, or non-text content that can't be backed up) `_clipboard_restore` returned early and the dictation just stayed there — which is precisely what the setting opts INTO. It now empties the clipboard instead, under the same generation guard so a newer paste is never clobbered. `Injector.keep_clipboard` mirrors the config (set at startup and in `_apply_runtime_setting`) because the clipboard helpers are static and never see the config. Guarded by `tests/test_clipboard_setting.py`.

- `2026-08-07` — Live Typing never retypes over a failed delete (v1.6.51). `_reconcile_live` ran `inject_stream(tail)` even when `delete_stream` came back False, appending the corrected text AFTER the characters it failed to remove — a visible mash of both versions. It now returns early and leaves the streamed text alone: still what the user said, just less polished, which beats garbled every time. Same rule the direct-inject paths already follow after a partial send. (The neighbouring "empty final pass but live-typed text exists → keep it" branch is NOT a bug and was left alone: those words are already in the user's document, and reporting "no speech" while they sit there would be worse.)

- `2026-09-14`: **A typed line break is Shift+Enter, never Enter (v1.6.79).** Reported with a screenshot: a dictation with a paragraph break went into ChatGPT, the message SENT at the break, and the rest landed in the box afterwards ("inserts it line by line, then enters straight away"). A paste cannot send, so the text had been typed: `_send_unicode` turned every `\n` into a bare VK_RETURN, which is Send in every chat composer. `_line_break_events()` now sends Shift+Enter (a new line in ChatGPT, Claude, Teams, Slack and ordinary editors). Three supporting fixes on the same path: (1) `_send_unicode_counted()` reports how many events SendInput accepted, and a PARTIAL send marks `_partial_direct` instead of falling through to a WM_CHAR re-send of the whole text, which would type it twice; (2) the paste gate polls up to `_FOREGROUND_GRACE_SECS` (0.3s) for the foreground to return to the target before refusing, because `popup._show_no_activate` briefly takes the foreground on the Tk thread and can land exactly as the gate reads it, while a real click into another window stays refused; (3) the clipboard readback retries OPENING the clipboard before calling it a mismatch, since a mismatch re-writes and wakes any clipboard listener again. **Why the paste was refused on Ryan's machine is NOT proven**: the exe discards stdout and `inject-failures.log` only recorded hard failures. Every fall back to typing now writes `fallback-to-typing: <reason> target=<exe> class=<cls> chars=<n> line_breaks=<n>` to `%LOCALAPPDATA%\FTC Whisper\inject-failures.log`, so the next occurrence names its cause. Guarded by `tests/test_typed_line_breaks.py`.

- `2026-09-23`: **Copy to Clipboard OFF restores what you had copied, images included (v1.6.93).** Asked for directly: copy an image, dictate, the dictation pastes, and the image is still there to paste afterwards. The paste path backed up CF_UNICODETEXT only, so an image, copied files or formatted text was lost (v1.6.51 then emptied the clipboard, which at least stopped the dictation lingering). `injector._clipboard_snapshot()` now copies every format whose handle is plain global memory (text, RTF, HTML, DIB, PNG, CF_HDROP, and the "keep out of clipboard history" flags a password manager sets) and `_clipboard_write_snapshot()` puts them all back, the approach AutoHotkey's ClipboardAll has used for years. Skipped: GDI and metafile handles (CF_BITMAP etc.; Windows rebuilds the bitmap from the DIB), the private and GDI-object ranges, and OLE plumbing (`DataObject`, `Ole Private Data`) that points at a live object in the source process. Only the first of CF_DIB/CF_DIBV5 is kept (Windows synthesises the other), which halves the copy. Bounded because it runs before Ctrl+V: 0.35s and 96 MB, text read first. Measured: a 1080p image costs ~45ms, text under 1ms. **Measured gotcha:** a clipboard listener can take the clipboard within ~50ms of a change even while we hold it open (ERROR_CLIPBOARD_NOT_OPEN mid-enumeration), so both read and write detect 1418 and retry the whole pass. Copy to Clipboard ON now never restores, so text the popup inserts stays on the clipboard as well as dictations. The ALT+R refine path saves and restores the same full snapshot. The native-target "non-text on the clipboard, type instead" routing is unchanged. Guarded by `tests/test_clipboard_setting.py`, including a real Win32 round trip that saves and restores the machine's clipboard around itself.
