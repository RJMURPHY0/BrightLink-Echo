# Decisions: Auth Signin

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-07-04` — auth unified onto the shared FTC Supabase project because older builds shipped a separate project whose user pool did not contain FTC Contacts accounts; legacy URLs in `_LEGACY_SUPABASE_URLS` are migrated on next launch.

- `2026-07-28` — Sign-in bars are **WHITE** (v1.6.38). Ryan's explicit, final call: the email/password fields are white bars with dark text (`field_bg` `#ffffff`, `field_text`/caret `#111`, subtle `#d4d4d4` border → accent on focus) on the dark card. This **reverses** the v1.6.36 "dark sign-in fields" decision — that pass read the white bars as the "white box" and darkened them; the bars are what Ryan actually wants white, and the flip-flop is why the sign-in never looked right across versions. Do NOT darken these bars again. Only `field_*` changed; `input_bg` (the "Continue with Google" button) stays dark. The page frame is dark (never a white border around the card).

- `2026-07-28` — Root cause of the sign-in "white box" found and fixed generally (v1.6.38): the size jump. `_atomic_ui` calls `geometry()` (a resize) **while WM_SETREDRAW is frozen**, and resizing a frozen window leaves the just-packed frame UNMAPPED — you get the previous frame's stale pixels plus a white strip where the window grew (proven in isolation; without the resize the swap maps cleanly). Fix: `_resize()` defers the `geometry()` call to `_pending_geometry` while `_in_atomic`, and `_atomic_ui` applies it AFTER redraw is back on. This also cures the long-standing login↔dashboard size-jump ghost. Guarded by `tests/test_app_window_sizing.py::ResizeDeferralTests`. NB: source runs under python.exe surface this reliably; the shipped exe masked it behind the debounced `_on_root_configure` heal.

- `2026-07-28` — Auto-login for returning users (v1.6.38): if a saved session exists at startup, show a "Signing you in…" splash (logo + animated dots) instead of the login form, restore in the background, and promote straight to the dashboard on success — the sign-in form is never shown on a normal launch. A 6s grace timer (`_reveal_login_if_pending`) reveals the form only if restore can't complete (slow Wi-Fi / offline); the retry keeps running and still promotes if the network recovers. Splash frame + `_switch_to_signing_in`/`_animate_signing_in`/`_cancel_signing_in` in `app_window.py`; the restore retry loop is unchanged. `_fire_authenticated` still fires exactly once (on promote, or on manual sign-in after reveal).

- `2026-08-06` — Reboot no longer forces a re-sign-in (v1.6.47). Root cause was a two-part race, not an expired session. A cold boot starts the app (logon task, no network gate) before DNS/TLS are up, so the restore overran the 15s wait; the old code ABANDONED the worker, returned False, and let the retry loop start a SECOND restore against the same on-disk refresh token. Supabase rotates refresh tokens, so the loser got `Invalid Refresh Token: Refresh Token Not Found` — which the error heuristic read as "credentials are dead" and **deleted a session the winner had just refreshed**. Meanwhile the retry loop's `if self._auth.is_authenticated: return` returned WITHOUT promoting, so a late success left the app authenticated behind the login form. Fixes: `_load_saved_session` runs at most one restore at a time (a second call joins the one in flight); the worker is never abandoned — it fires `set_restore_listener` and promotes late (`_promote_restored_session` via `_ui_after`); `_is_definitive_auth_error` tests NETWORK markers first and wins, so "not found"/"invalid" inside a DNS/TLS error never clears the file; a clear is additionally skipped when `self._user` is already set or the session bytes changed while in flight. UI: the splash grace went 6s→20s and will not reveal the form while `restore_in_flight` (it reschedules), a "Sign in manually" escape appears after 7s so nobody is trapped, and the retry backoff starts at 2s so a cold boot recovers in seconds. Guarded by `tests/test_session_restore.py`.

- `2026-08-13` — Sign-in and session restore made network-resilient (v1.6.65). Ryan's post-reboot "Sign-in failed: The read operation timed out" was three stacked things, all measured live: (1) his machine's network path (USB-dock Ethernet) blackholes in 30-60s windows after boot — reboot 13:01, NETLOGON couldn't reach the DC at 13:01:20, curl and Python both caught in later windows while the other worked — a MACHINE fault, not the app's; (2) supabase-auth ships NO timeout, so every auth round trip ran on httpx's 5-SECOND default and died inside those windows; (3) the restore retry loop had a finite ~13-min budget (30 attempts) and then gave up FOREVER — the app sat at the login form all session with a valid session file on disk. Fixes: `_get_client` passes `SyncClientOptions(httpx_client=httpx.Client(timeout=Timeout(30.0, connect=15.0)))` (guarded so an SDK rename degrades to defaults, never kills auth — proven live: a request that STARTED inside a blackout completed at 30.3s with the server's verdict, where 5s guaranteed death); `sign_in` classifies network errors FIRST (same rule as `_is_definitive_auth_error` — a TLS error carrying "invalid" must not read as wrong password), retries once after 1.5s, and reports "Can't reach the sign-in server" instead of raw httpx text; the restore loop keeps its burst then settles at a steady once-a-minute retry FOREVER (exits only on success, cleared file, or manual sign-in — the reveal after the burst no longer ends the loop). Guarded by `tests/test_session_restore.py::test_retry_loop_never_gives_up_while_a_session_file_exists`. Auto sign-in after reboot + update was already sound (session file in `%APPDATA%` untouched by the exe swap); it just needed the transport to stop lying.

- `2026-08-18` — Auto sign-in survives a slow-network boot, and restore failures are finally visible (v1.6.70). Reported: "literally every restart makes me sign in again." Diagnosis on Ryan's live machine ruled out the usual suspects — the mutex is fine (the two `FTC Whisper.exe` processes are the normal onefile bootloader parent + child, not two instances), the stored token is a standard 60-min Supabase access token, and the `.session`/`last-email.txt` mtimes matched a MANUAL sign-in, confirming auto-restore failed that boot. Root: his dock's NIC blackholes for the first 30-90s after a cold boot (documented v1.6.65), so the first restore attempts fail — and `_reveal_login_if_pending` only HELD the splash while `restore_in_flight` was literally true, i.e. only while a request was actively hanging; between backoff attempts it flipped to the login form, which reads as "you've been signed out", so he signed in by hand. Fix: while a valid session file still exists on disk the "Signing you in…" splash STAYS UP and keeps polling — the form is shown only on a definitive auth failure (which clears the file) or via the "Sign in manually" escape (already shown 7s in). The forever-retry loop then promotes to the dashboard the moment the network wakes, with no manual step. The attempt-30 burst-reveal was removed for the same reason. Second, and the reason this took so long to pin: a windowed exe (`console=False`) DISCARDS stdout, so every `[Auth] Session restore failed …` print vanished and the real cause could never be seen. `auth.py` now appends every restore outcome (attempt / OK / late-OK / network-retry / ignored-stale / **DEFINITIVE-cleared** / manual sign-in) to `%LOCALAPPDATA%\FTC Whisper\auth-restore.log` (size-capped, never raises), bracketed by boot/promote markers the UI writes via `AuthManager.note()`. If any reboot still fails, that log now names the exact reason. Guarded by `tests/test_session_restore.py` (splash-holds-while-session-exists, loop-only-reveals-on-clear).

- `2026-09-25`: **Sign-in keeps the dashboard's shape, and the impact range bar moved above the cards (v1.6.96).** Reported with a screenshot: the sign-in page looked squashed. It sized itself to its own form (floor 460px), so the window went 420×460 against a 670px dashboard, and the card was packed `fill="both", expand=True`, so any spare height became an empty band under "Forgot password?". Now the logo + card are one block (`LoginWindow._stack`) centred vertically in a page that holds the host's height (`embed(base_height=self._natural_dash_h)`), and `_fit_card()` sizes the card canvas to exactly what the form asks for (a canvas window item never propagates its child's size). Create Account (663px) fits the same 670, so switching modes no longer resizes the window; the page grows only when a form needs more (a status message on Create Account), which was previously clipped. The measured `_CHROME_H` is gone: `content_height()` reads the block directly. Separately, Ryan's call: the words-dictated bar sits ABOVE the three impact cards, words on the left and the range picker on the right (`_build_impact_range_bar`). `RangePicker(prefer_below=True)` drops down and right-aligns its panel under the control, rising only when the monitor has no room below; the default `_opens_above` behaviour is unchanged for any other caller. The breakdown panel still replaces bar + cards together, so its height is unchanged. Gap names kept (`impact_cards` = title → bar, `cards_words` = bar → cards) so a pushed `dashboard_gaps` still applies. Guarded by `tests/test_signup_payload.py`.
