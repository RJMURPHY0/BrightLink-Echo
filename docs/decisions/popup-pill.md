# Decisions: Popup Pill

Moved verbatim from CLAUDE.md on 2026-09-29. Add new decisions as a dated entry at the bottom. 

- `2026-08-07` — Multi-monitor placement (v1.6.51). `winfo_screenwidth()`/`winfo_screenheight()` report the **primary display only**, so every clamp and centre built on them dragged the widget back onto the main monitor when the app sat on a second screen — the words-range dropdown opening on another display. New `_monitor_work_area(widget)` (MonitorFromWindow + GetMonitorInfoW, `rcWork`, virtual-screen coords so left/top go negative) now backs `Dropdown.open`, `_resize`'s recentre, `_saved_dash_size`'s clamp, `show_toast` and `_show_login_screen`; it degrades to the old Tk numbers for anything without an HWND (test doubles). `popup.py` was already monitor-aware and is untouched. Guarded by `tests/test_multi_monitor.py`.

- `2026-08-09` — The popup actually stays on top now (v1.6.52), and the fix is two discoveries. (1) **tkinter's `winfo_id()` is a CHILD window on Windows** — the wrapper Tk really manages is its parent (measured: child exstyle `0x04`, parent `TOPMOST|TOOLWINDOW`). Every Win32 call aimed at `winfo_id()` therefore hit the wrong window: `_reposition` already used `GetAncestor(GA_ROOT)` for its physical-bounds check, but Z-order and repaint did not. `_top_hwnd()` resolves it once and caches it. (2) **`SetWindowPos(hwnd, HWND_TOPMOST, …)` on a window that is ALREADY topmost fails outright** — returns 0, Z-order does not move (measured both ways). `-topmost` only puts a window IN the topmost band; the taskbar and every other always-on-top window share it, and whichever was raised last wins, which is how the recording pill ended up behind the taskbar after an app switch. `_assert_topmost()` therefore raises with **`HWND_TOP`** (HWND_TOPMOST only re-establishes the band when the flag has been lost), under `SWP_NOACTIVATE` so a re-assert never takes focus off what the user is typing into. Once at show time is not enough — the pill is up for the whole dictation while the user switches apps — so `_keep_on_top()` re-asserts every 500ms for as long as `_mode` is set, and stops in `_do_hide`. Proven live: a rival always-on-top window raised over the pill, pill back in front within the tick.

- `2026-08-09` — Popup ghosting fixed at the source (v1.6.52): moving or resizing a MAPPED `overrideredirect` window lets Windows blit the old pixels into the new position. `_reposition` now repaints when the geometry actually changed — **size counts as a move**, because the caption bar grows downward while the pill is bottom-anchored — via `RedrawWindow(RDW_INVALIDATE|RDW_ERASE|RDW_ALLCHILDREN|RDW_UPDATENOW)` plus an `after(0)` twin, since `RDW_UPDATENOW` only validates Tk's update region and Tk paints on a later mainloop spin. `_repaint_popup` refuses hwnd 0 (`RedrawWindow(NULL, …)` repaints the DESKTOP). Same shape as the `_atomic_ui` fix in `app_window.py`.

- `2026-08-09` — Space no longer kills a live recording (v1.6.52). Space/Enter dismiss belongs to the post-insert badge ALONE, but nothing unhooked it when a new dictation started: `_enter_status_mode` never called `_unregister_space_dismiss()`, and the badge's own auto-dismiss timer returns early on a mode change, so the hook outlived its badge **forever**. A space typed mid-dictation then hid the pill. Now every entry into status mode clears it, and a fired-late icon timer unhooks when its badge is gone — but returns untouched while `_mode == "icon"`, because a NEWER badge owns the hook by then and unhooking it would break the badge that is actually on screen. Guarded by `tests/test_popup_topmost.py`.

- `2026-08-10` — The refine popup opens at the TEXT, not at the mouse (v1.6.53). `popup._reposition` picks its monitor from the coordinates it is handed, and `_on_refine_selection` handed it the raw `GetCursorPos`. Selections are routinely made with the keyboard, and on a multi-monitor desk the pointer is often parked on another screen — which is why the refine panel kept opening on the wrong display. `_refine_anchor()` prefers the caret from `_capture_focus_target` (real screen coords for the text being refined), then the mouse but ONLY when it is inside the target window's rect, then the window centre. Two silent dead-ends fixed alongside: the foreground guard compared against `popup._popup_hwnd`, which is tkinter's CHILD handle and therefore never what `GetForegroundWindow()` returns (so the panel could refine itself) — it now checks both handles via `_popup_hwnds()`; and a press while not IDLE returned with no feedback at all, which reads as a dead hotkey, so it now flashes "Finish dictating first". Guarded by `tests/test_multi_monitor.py::RefineAnchorTests`.

- `2026-08-10` — The recording pill stops fighting the taskbar, and rides a saved height nudge (v1.6.57). Two things, both reported live. **(1) Always-forward reverted.** v1.6.52 added `_keep_on_top()`, a 500ms `SetWindowPos(HWND_TOP)` re-assert that ran for the WHOLE dictation, so moving to the taskbar or switching apps buried them under the pill again on the next tick and the centred taskbar icons were unreachable. Removed from the recording-pill show path (`_show_no_activate`): the pill is raised ONCE at show (so it appears on top) and stays `-topmost` (above ordinary windows, so you can still see you are recording) but now YIELDS when the taskbar or another topmost window is raised — the pre-v1.6.52 behaviour. `_keep_on_top`/`_assert_topmost`/`_stop_keep_on_top` are kept and STILL used by the refine panel (`_expand_to_panel`), which is a focused interactive surface and is never up while the user reaches for the taskbar — do not strip them. **(2) Height nudge.** New `config.popup_offset` (px, default 30, clamped 0–400 on load) lifts the fixed popup ABOVE its `popup_height` baseline in `_reposition` (`y -= self._popup_offset`, applied in the FIXED branch only, then the existing work-area clamp still guards the top edge) — so out of the box the pill clears the taskbar instead of hugging it; offset 0 is the old hug-the-taskbar spot, still reachable. Two ▴▾ chevrons at the top/bottom-centre of the pill (`_pos_up`/`_pos_down`, placed on the status frame so they ride it with no separate show/hide) nudge it live by `_OFFSET_STEP` (18) via `_nudge_position`, which repositions and persists through `set_offset_saver` → `_on_settings_change("popup_offset", …)` (setattr + async save + runtime apply). WS_EX_NOACTIVATE lets the pill take the click without stealing focus (same reason the caption wheel works). The nudge is FIXED-placement only — the cursor-anchored refine panel stays at the caret. Guarded by `tests/test_popup_topmost.py::PositionNudgeTests` + the reverted `TopmostTests`. NB this and the v1.6.57 Dropdown-foreground-dismiss fix ship in the SAME release: both are "topmost surfaces must yield to the app you switched to".

- `2026-08-10` — Pill position arrows moved to the edge gutters + impact breakdowns gained icons and a fourth row (v1.6.58). **Arrows.** The v1.6.57 ▴▾ pair sat dead-centre over the waveform. Now four tiny 7pt triangles live in the pill's edge gutters: ▴ top / ▾ bottom fine-nudge the vertical `popup_offset`, ◂ / ▸ at the far edges step the NEW `config.popup_align` through left/centre/right (discrete, hard stop each end). The status frame padding went 14/10 → 16/16 so the 16px top/bottom gutter clears the 36px waveform (measured: 7pt label ≈ 14px at y=1, clears by 1px). `_reposition` places x by `popup_align` in the FIXED branch only (cursor-anchored refine untouched). The per-value `set_offset_saver(fn(v))` was generalised to `set_settings_saver(fn(key,value))` (app wires it straight to `_on_settings_change`, so a nudge is setattr + async save + runtime apply); `_nudge_position`/`_nudge_h_position` share `_commit_position`. `popup_align` default "centre" is the shipped first-install position for everyone (the "super-admin default" — there is no runtime admin push for it; the config default IS the default). **Impact panels.** Time-saved: the headline ("8.5 hrs" + "saved so far") now rides the header row via `_panel_head(headline=…, headline_sub=…)` instead of its own y=50 line, which freed the body for a fourth row — **Typing by hand** (`words / TYPING_WPM`, the counterfactual; it is also the largest figure so it anchors the bars). Every row in BOTH the time and speed drawers now leads with a `_row_icon` (reuses `ui_render.icon_glyph`, blended on `C["surface"]`, label indented to pad+24, bar/note stay full-width so long notes don't newly wrap): Dictation=mic, AI refine=wand, Time using it=clock, Typing by hand=keyboard; You=mic, Typing=keyboard, Handwriting=pen. Two NEW glyphs added to `icon_glyph`: `clock` and `pen` (drawn in the same 24-grid style). Four-row layout: `top=48`, `step=max(38,(h-82)//3)`, hairline between the two savings and the cost/counterfactual. Guarded by `tests/test_impact_panel.py::TimePanelTests` (now four rows + icon presence + headline-in-header + no-wrap/no-overflow) and `tests/test_popup_topmost.py::PositionNudgeTests` (▴▾ offset + ◂▸ align stepping/clamp/persist). NB the up/down arrows sit in the gutters but are still horizontally centred, i.e. directly above/below the wave, not over it.

- `2026-08-10` — Pill position arrows redrawn as edge triangles, verified by screenshot (v1.6.59). The v1.6.58 arrows were tk.Labels: a Label's height is its font line-height (~19px), too tall for the gutter, so ▲▼ still crowded the 36px waveform (the ◀▶ side arrows were already fine). Now each arrow is a small triangle drawn on its own tiny `tk.Canvas` (18×10 for ▲▼, 10×18 for ◀▶) pinned FLUSH to the four edges, sitting in 18px gutters — exact pixel size, so ▲ clears the wave above and ▼ below with a visible gap, and nothing ever sits over the timer/waveform/label. No Label = no font-height bloat and no opaque box (the canvas bg only falls on the bare gutter). Hover recolours the polygon via `itemconfigure("tri", …)`. NB `Canvas.lift()` is `tag_raise` (canvas items), NOT the widget raise — do not call it to stack the arrow; they are created after the content so they already draw on top. Verified before shipping by rendering the real pill headless and screenshotting it (a DPI-aware `SetProcessDpiAwareness(2)` in the harness so `GetWindowRect` and PIL `ImageGrab` share physical coords — a non-aware grab captured the wrong region). The default is confirmed **bottom-centre, 30px up** (`popup_height="low"` + `popup_align="centre"` + `popup_offset=30`), which is the first-install position for every user. Rule of thumb for these arrows going forward: they only ever live on the edges, never over anything on the bar.

- `2026-08-10` — Pill arrows pushed hard to the edges (v1.6.60). Each triangle's tip now reaches 1px from its canvas edge and the side gutters widened (padx 18→22, pady 18→16) so the ◀ ▶ no longer crowd the timer/"Recording" label while still hugging the very edges; ▲ ▼ likewise sit a hair off the top/bottom with the waveform clear between them. Screenshot-verified again. Rule stands: arrows only ever live on the edges, tiny gap to the edge, never over content.

- `2026-08-10` — Pill arrows now land on the real box border (v1.6.61). Root cause of every prior "still crowding the content" round: **tk `place()` on a frame with `padx/pady` measures from the INNER padded corner**, so `place(x=0, y=0)` pinned the arrows to the content edge, not the box edge (diagnosed: with padx=22/pady=16 the arrows sat at winfo x=22/y=16, exactly on the timer/waveform). Fix: the frame padding IS the arrows' gutter (`_STATUS_PAD_X=30`, `_STATUS_PAD_Y=24`), and each arrow is placed with a NEGATIVE offset (`y=-_STATUS_PAD_Y`, `x=-_STATUS_PAD_X`, and `+PAD` past `rely/relx=1.0`) so it lands on the true border with the tip ~1px off the edge, well clear of the content in the wide gutter. Verified by dumping `winfo_x/y` of the frame and all four arrows (up y=0, down flush at the bottom, left x=0, right flush at the right) plus a screenshot. Guidance for anyone touching pill overlays: `place()` coords are relative to the PADDED region — offset by the pad to reach the frame's true edge.

- `2026-08-11` — Pill restored to its original size with the edge arrows kept (v1.6.62). v1.6.61's generous gutters (padx 30/pady 24) put the arrows on the border but inflated the pill (84px tall). `_STATUS_PAD_X/Y` are back to the original 14/10 (pill is 56px again, exactly as before the arrow work), and the triangles were shrunk to fit those gutters (up/down 16×6, left/right 6×16) so they still sit on the box border via the negative-offset placement, with a ~4px gap to the content. Screenshot- and geometry-verified (292×56, arrows at x=0 / y=0 / far edges). Size is now driven purely by the padding + the small triangles; do not grow the padding to move the arrows out — they already reach the true edge through the negative offset.

- `2026-08-13` — The popup opens on the monitor of the WINDOW receiving the text (v1.6.63). Third anchor policy; the first two both shipped and both put the pill/refine panel on the wrong screen. (1) The caret (v1.6.53): Chromium/Electron apps expose no caret via GetGUIThreadInfo, so the anchor fell back towards (0,0) and the popup landed on the primary display. (2) The raw mouse: dictation and refine are keyboard flows, and the mouse is routinely parked on a DIFFERENT monitor from the app being typed into (Ryan pressing ALT+V in the Claude app on one screen while the mouse sat on the Pipedrive screen: pill opened at the mouse). `_popup_anchor(hwnd)` in app.py returns the centre of the foreground window's rect (GetWindowRect works for every app class, no accessibility involved), cursor only as fallback (hwnd 0, unreadable/empty rect, or IsIconic). Used by the recording pill, the Transcribing state and refine. `_rec_cursor_x/y` is still the TRUE mouse position: injection's same-cursor check and the browser DOM-focus click depend on it, so the anchor rides separate fields (`_rec_anchor_x/y`). Verified live on the real 3-monitor rig (scratch harness: window on each monitor, anchor resolved to that monitor every time while the cursor sat on another screen). Guarded by `tests/test_multi_monitor.py::PopupAnchorTests`, including a source-level guard that the caret never comes back.

- `2026-08-13` — Popup anchor, fourth and final policy (v1.6.64): the v1.6.63 window-CENTRE anchor still misplaced refine on Ryan's rig (he was on screen 2, refine opened on screen 3; his app had already self-updated to 1.6.63, verified against the running pid). Diagnosis facts, all measured live: the app process is DPI-UNAWARE; the laptop display virtualises to 1280x800 in its coordinate space (150% scale) while both externals are 100%; screens 3 and 2 share the x=1920 edge; and the REAL FloatingPopup pipeline (pill, badge, panel), driven end-to-end in a repro harness, lands correctly when the target window sits cleanly on one monitor — so the residual failure is the anchor POINT for a window that STRADDLES the shared edge, where the centre (and any window-derived point) can land on the half the user is not working in. `_popup_anchor` priority is now: (1) the MOUSE when it is inside the target window's rect — the user just clicked/selected there, and it is the only signal that says which side of a straddling window they are on; (2) the window's own monitor via MonitorFromWindow (largest intersection), returned as that monitor's work-area centre — the parked-mouse case; (3) the mouse wherever it is. Never the caret (v1.6.53 failure: unreadable in Chromium/Electron). Every anchor decision and every `_reposition` placement now writes one line to `%TEMP%\ftc_pos_debug.log` (`popup.pos_log`, self-capping at ~256KB), so any future wrong-screen report comes with the exact inputs. Guarded by `tests/test_multi_monitor.py::PopupAnchorTests`.

- `2026-08-13` — Two popup options (v1.6.64), both in Settings and applied live: `show_pill_arrows` (default on) hides the ▴▾◂▸ nudge arrows for a clean pill — place() specs are captured at build time because place_forget drops the geometry, so a re-show restores the exact negative-offset border placement; `hide_popup_in_screenshots` (default off) sets SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE, 0x11) so the pill/badge/refine panel stay visible to the user but vanish from screenshots and recordings (Win10 2004+; the call must target `_top_hwnd()`, NOT `winfo_id()` — the child-window gotcha again: affinity on the child succeeds silently and does nothing). Both flags are pushed at startup before the popup window exists and re-applied at initialize. New `camera` glyph in `ui_render.icon_glyph`. Guarded by `tests/test_popup_options.py`.

- `2026-08-13` — **The wrong-screen saga's ACTUAL root cause found and killed (v1.6.65): shared-windll poisoning.** `ctypes.windll` is CACHED — `windll.user32` is ONE object per process, so `app_window._monitor_work_area` (v1.6.51) pinning `GetMonitorInfoW.argtypes = [c_void_p, POINTER(app_window._MONITORINFO)]` rewrote the signature for EVERY module. popup's `_get_monitor_workarea` passes `byref(popup._MONITORINFO)` (a different class object) → `ctypes.ArgumentError` on every call → swallowed → fallback `(0,0,winfo_screenwidth,winfo_screenheight)` = the PRIMARY monitor. Same death in `app._window_monitor_centre` (it imports popup's struct). So from v1.6.51 every popup placement collapsed to the main display no matter what the anchor said, and all four anchor-policy releases (v1.6.53→v1.6.64) fought the wrong layer. The repro harnesses drove FloatingPopup WITHOUT AppWindow, so the poisoning never fired in testing — which is why every fix "verified live" then failed in the shipped exe. Proven with the v1.6.64 pos log (`anchor → (2751,960) via=cursor-in-window` then `place wa=(0,0,1920,1080)`, the fallback shape) plus an isolated repro. Fix: **argtypes/restype only ever go on PRIVATE `ctypes.WinDLL("user32")` instances** — `app_window._user32()`, `popup._monitor_user32()` (used by app.py too), and app_icons/app.py migrated off the shared cache (injector already did it right). Guarded by `tests/test_multi_monitor.py::SharedUser32HygieneTests`: shared-cache-stays-untyped, popup + anchor survive `_monitor_work_area` running FIRST (the poisoning order), and a static ban on `windll.<dll>.<fn>.argtypes =`. Rule for all future Win32 typing: `ctypes.WinDLL("x")` per module, NEVER type `ctypes.windll.x`.

- `2026-08-14` — The refine popup's mic moved INSIDE the Ask bar (v1.6.67), and two rendering bugs fell out of it. (1) `_RoundedField` gained a `trailing` slot: the widget is pinned to the field's right edge, centred on the full height, and the text's usable width shrinks by it — inset by its own `trailing_inset` rather than by `pad`, so a button taller than one text row still sits in the curve. (2) **`app_window._rr` draws roughly HALF the radius you ask for.** It is a `create_polygon(smooth=True)` B-spline, which does not pass through its control points, and Canvas polygons have no anti-aliasing — so the bar read as barely rounded however high the number went. `_RoundedField._paint` now uses `ui_render.round_rect` (PIL, cached, true radius) and falls back to `_rr` only if PIL is missing. (3) **`Text.count(..., "displaylines")` returns line BOUNDARIES, not lines** — text occupying three wrapped rows answers 2. All three auto-sizing Texts in the popup (Ask box, live captions, AI result) fed that straight into `configure(height=…)` and had therefore always rendered one row short, clipping the last line. Fixed once in `popup._display_lines()`. NB for tests: Tk only dispatches an `event_generate("<KeyRelease>")` to the widget that HOLDS FOCUS — without `focus_force()` the event goes nowhere and a search-bar test passes for the wrong reason.

- `2026-08-17` — The post-insert badge dismisses on ANY key and on switching apps (v1.6.68). It previously bound Space and Enter ONLY, so any other typing left it sitting there. Now one global `keyboard.hook` (suppress=False — this only ever observes, every keystroke still reaches the app) plus a 250ms foreground poll that hides the badge once `GetForegroundWindow()` is no longer the window the text was injected into. Both are gated behind `KEY_DISMISS_GRACE_SECS` (**1.2s**), because the badge appears the instant the text lands: without a grace the keystroke the user was already mid-way through typing — or the focus settling after `_show_no_activate` hands foreground back — kills it before they can register the ✓, which reads as a flicker rather than a confirmation. The grace applies **uniformly to every key including Space and Enter** (Ryan's "any button" has to mean any button; a rule with exceptions is one the user has to learn), and `armed_at` is captured at registration so a newer badge cannot extend an older hook's grace. Key **DOWN only** — the hotkey's own key-up arrives after the badge is drawn. Two carve-outs: a "⚠ Not inserted" badge does NOT follow the user away (it is the one badge worth reading after switching apps), and the refinement panel carries neither hook (the user is typing into the Ask box, and the panel deliberately TAKES focus so a target-keyed watch would hide it the moment it opened). `_foreground_is_target` fails OPEN and counts both popup handles as "ours" — `winfo_id()` is a CHILD window, the gotcha `_top_hwnd` documents. NB the v1.6.52 unhook-on-mode-change contract matters MORE now, not less: an orphaned hook would kill the recording pill on the first character typed, not just on a space. Guarded by `tests/test_popup_topmost.py::KeyDismissTests`.

- `2026-08-19` — The refine popup's voice prompt stops overwriting the Ask box (v1.6.71). The mic re-transcribes the WHOLE audio buffer on every ~1.6s preview and the result went straight in through `_set_ask_entry`, so anything the user did by hand was undone the moment they spoke again: delete the box mid-sentence, keep talking, and every deleted word came back (reported live against the CRM's chat Ask bar, which had the identical defect and was fixed in the same pass). Voice writes now go through `_apply_voice_text`, which remembers the exact string it last wrote: anything else in the box means the user edited it, so that content becomes the base and the words spoken BEFORE the edit are dropped. The drop is **word-indexed, never a byte prefix** — each pass re-transcribes the same audio and may re-word or re-punctuate what it produced last time. Second half: submitting the instruction (Enter or ✦ Ask) calls `_stop_voice_capture()`. A mic left listening kept rewriting a box the user had already sent, and the capture's final blocking pass landed after the ask had gone; the stop bumps `_voice_token` so that late write is dropped. A normal ⏹ stop deliberately does NOT bump it — that final pass is the cleanest transcription and must still land. Closing the panel takes the same path. Guarded by `tests/test_voice_prompt_edit.py`.

- `2026-08-19` — The ✓ badge stops ignoring the first key you press (v1.6.71). `KEY_DISMISS_GRACE_SECS` 1.2 → **0.25**, reported as "there's a delay where I can press any button and it won't go away" — at 1.2s the badge visibly ignores the user, which reads as stuck rather than as a confirmation. The long window was really absorbing two things, and both are now filtered by IDENTITY instead of by time, which is what makes the short grace safe: (1) `_MODIFIER_KEY_NAMES` — the hotkey's own modifier is by definition still held as the badge appears, and a held key auto-repeats as a stream of fresh key DOWNs; (2) an auto-repeat guard seeded from `keyboard._pressed_events` at arm time, so the combo's base key, held for the same reason, never reads as a fresh press. What is left for the grace to cover is only our own injection's synthetic input still draining through the hook thread. This narrows the v1.6.68 "any button has to mean any button" rule on purpose: a modifier alone does nothing to the document, and Shift held to capitalise is not a dismissal. New `config.badge_dismiss_on_key` (default on) turns the behaviour off from Settings; it is read when a badge is ARMED, so the setting can never change under a badge already on screen. Guarded by `tests/test_popup_topmost.py::KeyDismissTests`.

- `2026-08-19` — The recording pill can be nudged BELOW the tier baseline (v1.6.71). `popup_offset` floored at 0, which is the "low" baseline just above the taskbar — a user who still wants it lower runs out of ▾ arrow there and the button looks broken. `_OFFSET_MIN` is now **-120**: a negative offset deliberately moves the pill down into the taskbar strip, and `_reposition` clamps that case against the monitor's FULL rect (`_monitor_bottom`, read from `rcMonitor` in the same `GetMonitorInfoW` call the work-area lookup already makes, so the two can never disagree about which monitor is in play) instead of its work area — clamping a deliberately-negative offset to the work area would silently undo every press past 0 and the arrow would look dead. Bounded, because a pill parked entirely off the bottom edge would be unrecoverable without Settings. `Config.load()` clamps to the same range, and a small negative value is now a legitimate user choice rather than a stray value coerced to 0. Persistence was already correct (`_commit_position` → `_on_settings_change` → setattr + `save_async`), so the nudged position survives a restart exactly as before.

- `2026-09-23`: **Screenshotting the badge no longer dismisses it (v1.6.92).** Reported: with Hide Popup in Screenshots OFF the ✓ / Echo badge still never appeared in a screenshot. The capture setting was fine (proven live: a screen grab shows the badge with it off and not with it on). The badge dismissed itself first, twice over: the `S` of Win+Shift+S and the PrtSc key counted as "any key", and the Snipping Tool overlay taking focus tripped the switched-apps check. `_key_dismisses_badge()` now ignores screenshot keys and any key pressed while a Windows key is held (shell shortcuts never type into the document), and `_foreground_is_target()` treats a screen-capture tool in front (`_CAPTURE_TOOL_EXES`, e.g. ScreenClippingHost, SnippingTool, ShareX) as still on the target. Whether the badge shows in the capture is now decided only by the setting. Guarded by `tests/test_popup_topmost.py::ScreenshotKeepsBadgeTests`.

- **NOT fixed, deliberately (v1.6.52):** `WS_EX_NOACTIVATE` is still applied to `winfo_id()`, i.e. to the child window, where it does nothing. The popup's no-focus-steal behaviour currently comes from the `SetForegroundWindow(prev_fg)` restore in `_show_no_activate`, not from the flag. Moving it to the real toplevel is the correct fix but changes load-bearing injection behaviour ("the critical fix for ChatGPT / browser inputs"), so it wants its own release and its own testing rather than riding along with a Z-order change.

- `2026-10-06`: **The pill is a per-monitor DPI window, placed and sized in real pixels (v1.8.2).** Reported: on the 150% laptop (screen 1, below two 100% screens) the pill opened mid-window instead of bottom-centre, though at the small size Ryan likes. The pos log showed placement maths in the app's scaled space (laptop work area 1280x752 at (949,1080)) while the window drew at those numbers as real pixels. Measured on the rig: for a DPI-unaware Tk BORDERLESS window, Windows picks both its scale and how to read its position from whichever app window was shown last. Dashboard open on a 100% screen: placed (1443,1700), lands at real (1443,1700) at 1x. Dashboard hidden or on the laptop: lands at (1690,2010) at 1.5x. Raw Win32 popups and framed Tk windows always scale. So the old maths was right only when the dashboard was hidden, and then the pill was 1.5x. Fix, per Ryan only the recording pill changes size: the popup is now TWO windows. The recording pill (recording and transcribing) lives in its own window that `initialize()` creates under a per-monitor-v2 thread DPI context (`_RealPixels`); the badge and refine panel stay in an ordinary DPI-unaware window, sized by Windows exactly as before, and `_use_window` swaps `self.root` between them per mode.
